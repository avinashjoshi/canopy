# Design: Upgrade UX overhaul

Generated by /plan-eng-review on 2026-04-30
Branch: upgrade-ux-overhaul-design
Repo: github.com/oncactus/canopy
Status: PROPOSED — awaiting implementation
Mode: Builder

## Problem statement

After v0.12.0 shipped the source-based install + `canopy upgrade` flow, three pain
points surfaced during dogfooding:

1. **No proactive signal.** `canopy upgrade` is purely pull-based — you only learn
   that v0.13 exists if you remember to run `canopy upgrade --check`. In practice
   nobody does, so users run weeks-old canopy without realizing it. The signal exists
   on GitHub; we just never look at it on the user's behalf.
2. **No way to act on the signal in-context.** Even if a user knew an upgrade was
   available while staring at the TUI, they'd have to detach the session, drop to a
   shell, run `canopy upgrade`, watch a 10-second stdout dump, and re-attach. The
   feedback loop spans terminals.
3. **Spartan upgrade output.** Today's `canopy upgrade` prints versions, the
   CHANGELOG slice, runs the shell, prints success — block-and-wait, no live
   progress, no confirm gate, no recovery affordance if `make install` fails
   mid-build.

Pain (1) and (2) compose: the satisfying UX is "TUI shows v0.13.0 is available,
press U, see what's new, confirm, watch it install, return to your work" — all
without leaving the TUI. None of those steps work today.

## What makes this cool

You're working in canopy. A pill appears in the top bar: `v0.12.3 ⇑ v0.13.0`. You
press `U`. The screen flips to a changelog view: bullets of what shipped since you
last upgraded. Press Enter. The screen flips again to a streaming pane: `git pull`
output, then `make install` output, scrolling live. Ten seconds later, green
checkmark, "Upgraded to v0.13.0." Press any key, you're back at the workspace list,
already running the new binary. Total interaction: 3 keystrokes, never left the TUI.

For users running canopy from outside a TUI (`canopy ls` in a shell, scripted
deploys), the signal still lands — a one-line hint at the bottom of `canopy ls`
output and an upgrade-available suffix in `canopy version`. Same cache, three
surfaces.

## Constraints

- **No background daemon.** The auto-check piggybacks on existing canopy
  invocations. Avi was firm on this in the v0.12.0 design discussion and we're
  honoring it.
- **Network never blocks the UI.** Every fetch is async or cache-first. A user on
  a flaky connection sees the previous-cached answer or no pill, never a hang.
- **Backwards compatible.** `canopy upgrade` from the shell keeps today's plain
  stdout behavior verbatim. Auto-check + TUI flow are additive, no existing call
  site changes shape.
- **DEV binaries are exempt.** `canopy upgrade` already refuses on DEV; the pill
  and TUI flow follow the same rule. No auto-check fires on DEV. (Rationale: a DEV
  binary's notion of "latest" is irrelevant — you're running uncommitted local
  code; whatever's on `main` is a different artifact.)
- **The TUI flow is in-TUI only.** Standalone `canopy upgrade` from the shell does
  NOT open a TUI. There's exactly one in-TUI surface for the fancy flow, reachable
  via the `U` key inside the unified TUI.

## Premises (locked, confirmed via interactive review)

1. **Cache-first synchronous read; async refresh on stale.** Every TUI startup
   reads `~/.canopy/upgrade-check.json` synchronously. If the cached
   `latest_version` is <6h old, render the pill from cache. If stale, fire a
   `tea.Cmd` that runs `fetchRemoteFile` in a goroutine; result lands as
   `upgradeCheckedMsg` and re-renders. (D1)
2. **Per-version dismissal, 6h TTL.** Cache schema:
   `{checked_at, latest_version, dismissed_version}`. Pill is suppressed when
   `latest_version == dismissed_version`. A new release un-suppresses
   automatically (because the field changes). 6h TTL chosen over the 24h industry
   norm because canopy's release cadence during active development is intra-day.
   (D2)
3. **Mutate the existing version pill + add a `canopy ls` hint line.** Two
   surfaces, one cache. The version pill gains an upgrade-arrow branch
   (`v0.12.3 ⇑ v0.13.0`); plain `canopy ls` prints a single dim hint line at the
   bottom. No 4th pill (top bar gets crowded), no banner (eats vertical space),
   no toast (auto-dismiss loses the signal). (D3)
4. **Dismissal works from CLI and TUI.** `canopy upgrade --dismiss` writes
   `dismissed_version = latest_version`. In the TUI, capital `D` does the same.
   Symmetric with the two-surface display. (D4)
5. **One TUI surface, in-TUI only.** Standalone `canopy upgrade` from the shell
   stays plain stdout (today's behavior + `--dismiss` flag). The fancy flow lives
   inside `internal/ui/upgrade.go` as a sub-model of the unified TUI, only
   reachable via the `U` key when the upgrade pill is showing. (D5)
6. **Full-screen mode swap, matches existing modes.** `upgradeMode` joins
   `drawerMode` / `busyMode` / `confirmDeleteMode` etc. View() dispatches to
   `renderUpgrade()`. Esc/q returns. No new overlay primitive. (D6)
7. **Reuse `safeBuffer` + tick pattern for streaming.** The existing `n`-flow's
   `safeBuffer` + ~150ms `progressTick` pattern handles the `git pull` +
   `make install` output. No new dep, no `bubbles/viewport`. Output is small
   (~50 lines total). (D7)
8. **Four-state flow: Loading → Preview+confirm → Running → Done.** Esc cancels
   at any pre-run state. Once running, ctrl-c kills the subprocess via context
   cancel. Error states render the captured stderr inline. (D8)
9. **DEV binaries are inert.** No auto-check fires on DEV. `U` and `D` keys never
   bind on DEV. The pill never appears on DEV. Consistent with `canopy upgrade`'s
   existing refusal.

## Architecture

### Filesystem shape

```
~/.canopy/
  upgrade-check.json            ← NEW. Cache file. JSON, 3 fields.
  src/                          ← existing (canopy upgrade git-pulls this)
  workspaces/canopy/<name>/     ← existing
  log/                          ← existing
  state.json                    ← existing

cmd/canopy/
  upgrade.go                    ← existing. Gains --dismiss flag.
  upgrade_check.go              ← NEW. Cache read/write + cachedRemoteVersion.
  upgrade_check_test.go         ← NEW.

internal/ui/
  upgrade.go                    ← NEW. upgradeMode + renderUpgrade + key handlers.
  upgrade_test.go               ← NEW.
  render.go                     ← edited. renderVersionPill gains upgrade-arrow branch.
  model.go                      ← edited. New mode constant + cache fields + Init cmd.
  update.go                     ← edited. U/D key bindings + new msg types.
```

### Cache file schema

```json
{
  "checked_at":        "2026-04-30T12:34:56Z",
  "latest_version":    "0.13.0",
  "dismissed_version": "0.12.3"
}
```

- `checked_at` — RFC3339 UTC. TTL is 6h: when `now - checked_at > 6h`, the
  cached `latest_version` is stale and an async refetch is scheduled.
- `latest_version` — bare semver from `VERSION` on `origin/main`. No `v` prefix
  (matches the file format used by `canopy upgrade`).
- `dismissed_version` — empty string by default. Set by `--dismiss` /
  capital-`D`. Pill is suppressed when this equals `latest_version`.

Schema is forward-compatible: extra fields on disk are preserved on rewrite. JSON
because trivial in Go and gives us a versioned shape we can extend (notification
counts, last-seen-changelog-hash, etc) without a migration.

### Auto-check data flow

```
TUI startup (route.go RunUnified)
  │
  ├─ versionDetails() → if IsDev, skip auto-check entirely. Done.
  │
  ├─ readUpgradeCheckCache()
  │     │
  │     ├─ cache present + checked_at < 6h ago
  │     │     → SetUpgradeAvailable(latest_version, dismissed_version)
  │     │     → no network call this invocation
  │     │
  │     ├─ cache present + checked_at >= 6h ago
  │     │     → SetUpgradeAvailable(latest_version, dismissed_version)  ← stale-but-shown
  │     │     → schedule tea.Cmd: fetchRemoteFile + writeUpgradeCheckCache
  │     │     → on result: upgradeCheckedMsg → re-render with fresh value
  │     │
  │     └─ cache missing (first run)
  │           → SetUpgradeAvailable("", "")  ← suppressed
  │           → schedule tea.Cmd: fetchRemoteFile + writeUpgradeCheckCache
  │           → on result: upgradeCheckedMsg → first render with pill
  │
  └─ Bubbletea program runs.

Network failure path:
  fetchRemoteFile errors  →  upgradeCheckedMsg{err: ...}
                          →  Update logs at debug, leaves model state unchanged
                          →  pill shows last-cached value or stays suppressed
                          →  next invocation retries (cache wasn't updated)
```

### Pill rendering

`renderVersionPill` in `internal/ui/render.go` gains a fourth branch (in priority
order):

1. `devWorkspace != ""` — cyan DEV pill (unchanged).
2. `versionLabel == ""` — no pill (unchanged).
3. `upgradeAvailable && !dismissed` — release pill with **yellow up-arrow + new
   version**: `v0.12.3 ⇑ v0.13.0`. Pill body stays muted gray, the arrow + new
   version are foreground-yellow (`220` in the lipgloss palette) for the eye to
   catch.
4. else — muted gray release pill (unchanged).

The yellow arrow is the only color shift; pill body color stays gray to avoid
clashing with the violet brand pill or the cyan DEV pill. The arrow glyph is `⇑`
(U+21D1, double-stroke up arrow) — rendered widely, no Nerd Font dependency.

## `canopy ls` hint line

When the same cache logic runs from a non-TUI invocation (e.g., `canopy ls`), the
existing plain-text output gains one final dim line:

```
NAME                STATUS   ...
add-oauth-login     ready    ...
fix-broken-header   stopped  ...
                                   ← existing output ends here
canopy v0.13.0 available — run `canopy upgrade`.   ← NEW (only when upgrade available)
```

Suppressed when:
- DEV binary
- Cache missing
- `latest_version == dismissed_version`
- `latest_version` matches running version

## Subcommand changes

### `canopy upgrade --dismiss` (new flag)

```
$ canopy upgrade --dismiss
Dismissed v0.13.0. Pill will reappear when v0.13.1 or later ships.
```

Writes `dismissed_version = latest_version` in the cache. No network call (uses
the cached value). Refuses if no cached `latest_version` (nothing to dismiss).
Refuses on DEV (no auto-check on DEV, nothing to dismiss).

### `canopy upgrade` (existing flow, unchanged behavior)

Still does today's plain stdout flow: fetch VERSION, compare, print CHANGELOG
slice, run shell. No tty detection. No TUI bridging. The TUI flow is reachable
only via the `U` key in the unified TUI, by design.

After a successful upgrade (CLI or TUI), the cache is rewritten:
`checked_at = now`, `latest_version = current_version`,
`dismissed_version = ""`. This makes the pill disappear on the next invocation
without waiting for the 6h TTL.

## Approaches considered

### Approach A: Background daemon polling GitHub (REJECTED)

A small `canopyd` background process polls GitHub every N minutes, writes the
result to a socket or file. Most "real" CLIs that ship snappy update banners do
this (gh CLI offloads to a `gh-update-checker` goroutine that survives across
invocations via shared cache).

**Why rejected:** Avi was firm on no daemons in the v0.12.0 design discussion.
Canopy's invocation model is per-shell, not per-machine. A daemon adds lifecycle
problems (start, stop, restart on upgrade, log rotation, "is it running?")
disproportionate to what we're solving. Cache-on-disk gives us 95% of the same
ergonomics.

### Approach B: Sync network call on every `canopy` invocation (REJECTED)

Block on the GitHub fetch every time canopy starts. Trivial to implement (no
goroutine, no message routing). Adds 50-200ms to every TUI startup; tmux popup
opens feel sluggish; offline users see a hang.

**Why rejected:** Network on the hot path. The async-refresh pattern (Approach C)
costs the same code volume and never blocks.

### Approach C: Cache-first sync read + async refresh on stale (CHOSEN)

Synchronous cache read from disk → instantly render whatever we last saw.
Schedule an async refetch via `tea.Cmd` only when the cache is stale or missing.
Network failure leaves cache unchanged; next invocation retries.

**Why C wins:** Industry-standard pattern (npm `update-notifier`, cargo,
homebrew, `gh` all use it in some form). Cache hit = zero latency. Cache stale =
async, no UI block. Network failure = silent degradation. Single fetch path
shared with `canopy upgrade` (`fetchRemoteFile` already exists in `upgrade.go`).

### Approach X: Standalone CLI TUI for `canopy upgrade` (REJECTED)

Original plan included tty-detection in `canopy upgrade` CLI: when stdout is a
tty, open a Bubbletea program for the upgrade flow; when piped, stay plain
stdout.

**Why rejected:** Avi pushed back during the review with "for upgrade from cli, i
dont think it needs a tui." Correct intuition. Two TUI entry points (`canopy
upgrade` standalone + in-TUI `U` key) would duplicate rendering logic, double
test surface, and the "press U inside the TUI" path is the actually-valuable
moment. Collapsing to one in-TUI surface dropped ~150 LOC of Cobra→Bubbletea
bridging without losing UX value.

### Sub-decisions within the chosen approach

- **6h TTL vs 24h industry norm.** 6h, because canopy ships intra-day during
  active development; 24h would mean other workspaces don't see the pill until
  the next day. Async-only fetch makes shorter TTL effectively free.
- **Mutate the version pill vs add a 4th pill.** Mutate. 4 pills won't fit on
  narrow terminals, and the version pill IS the natural surface for "what
  version's running and is there a newer one."
- **Per-version dismissal vs time-based snooze.** Per-version. "I don't want
  v0.13" usually means "until v0.14 ships," not "for 7 days then ask again."
- **Reuse `safeBuffer` vs adopt `bubbles/viewport`.** Reuse. ~50 lines of
  subprocess output doesn't justify a new dep + new pattern.

## Implementation plan

Single PR, four logical commits. Each ships standalone.

### Commit 1: cache scaffolding (`upgrade_check.go`)

Pure non-UI plumbing. Zero TUI changes. Lands first because everything else
depends on the cache.

- `cmd/canopy/upgrade_check.go` (new):
  - `upgradeCheckPath()` → `~/.canopy/upgrade-check.json`
  - `readUpgradeCheck(path) (*upgradeCheck, error)` — JSON unmarshal, missing
    file is not an error (returns nil, nil)
  - `writeUpgradeCheck(path, *upgradeCheck) error` — atomic via tempfile +
    rename, same pattern as state.go
  - `cachedRemoteVersion(ctx, srcDir) (latest, dismissed string, err error)` —
    the public entry. Reads cache; if fresh, returns immediately; if stale,
    fetches via `fetchRemoteFile` (already in upgrade.go), writes cache,
    returns. Caller chooses sync vs async.
- `cmd/canopy/upgrade_check_test.go` (new): missing cache, fresh cache, stale
  cache + successful refetch, stale cache + network failure, dismissed-equals-
  latest suppression logic, atomic write race regression. ~12 cases.

### Commit 2: `canopy upgrade --dismiss` + `canopy ls` hint line

Surface the cache from the existing CLI commands. Still no TUI.

- `cmd/canopy/upgrade.go`: add `--dismiss` flag. Refuses on DEV; refuses if no
  cached latest. Writes `dismissed_version = latest_version`. Prints
  confirmation line.
- `cmd/canopy/ls.go`: at end of output, when not DEV and `latest_version != ""`
  and `latest_version != dismissed_version` and `latest_version != current`,
  print the dim hint line. Behind the same gates as the pill.
- After-upgrade cache rewrite: at the end of `runUpgrade` (success path), update
  cache with `checked_at = now`, `latest_version = current`,
  `dismissed_version = ""`. So the pill disappears immediately post-upgrade
  without waiting for the next 6h refresh.
- Tests: dismiss happy path, dismiss without cached latest, dismiss on DEV,
  ls-with-upgrade-available, ls-with-dismissal, post-upgrade cache rewrite.

### Commit 3: pill mutation + auto-check wiring on TUI startup

Wires the cache into the existing top-bar pill. No new mode yet.

- `internal/ui/render.go`: extend `renderVersionPill` with the upgrade-arrow
  branch (priority 3 above). Style: gray pill body (existing) with foreground
  yellow `220` arrow + new version inline.
- `internal/ui/model.go`: add `upgradeLatest, upgradeDismissed string` fields
  on Model. Add `SetUpgradeAvailable(latest, dismissed string)` setter.
- `internal/ui/model.go RunUnified`: before `tea.NewProgram`, call
  `cachedRemoteVersion` synchronously (cache-only, no network) and pass result
  via `SetUpgradeAvailable`. Schedule a `tea.Cmd` for async refresh as part of
  `Init()` if cache was stale/missing.
- `internal/ui/update.go`: handle `upgradeCheckedMsg{latest, err}` — update
  fields, write cache, no-op on err.
- Tests: pill render — release-no-upgrade, release-with-upgrade,
  release-with-upgrade-but-dismissed (no pill mutation), DEV (no upgrade pill
  ever). Auto-check wiring tested via fake `cachedRemoteVersion` injectable
  seam.

### Commit 4: in-TUI upgrade flow (`U` key, upgradeMode, four-state model)

The fancy flow. Reuses `safeBuffer` and the tick pattern verbatim from busyMode.

- `internal/ui/upgrade.go` (new):
  - `upgradeState` enum: `loading`, `preview`, `running`, `doneOK`, `doneError`.
  - Model fields: `upgradeState`, `upgradeChangelog`, `upgradeBuf *safeBuffer`,
    `upgradeOutput`, `upgradeErr`, `upgradeCancel context.CancelFunc`.
  - `enterUpgradeMode()` — sets mode, fires `loadChangelogCmd`.
  - `loadChangelogCmd()` — `tea.Cmd` calling `fetchRemoteFile` + `changelogSlice`
    in a goroutine.
  - `runUpgradeShellCmd()` — `tea.Cmd` calling `upgradeRunShell` with the
    safeBuffer as both stdout and stderr; cancellable via `upgradeCancel`.
  - `progressTick()` — same as busyMode's tick: ~150ms, drains the buffer into
    `upgradeOutput`, schedules next tick.
  - `renderUpgrade(*Model) string` — branches on `upgradeState`, renders the
    four states.
  - Key handlers: Enter from preview → run; Esc from preview/loading → exit
    mode; D from preview → dismiss; Ctrl-C from running → cancel.
- `internal/ui/update.go`: bind `U` (only when `m.upgradeAvailable() == true`)
  to `enterUpgradeMode`. Bind `D` similarly to dismiss.
- `internal/ui/view.go`: add `case upgradeMode: return m.renderUpgrade()` in
  `View()` switch.
- `internal/ui/help.go` (existing renderHelp): add U/D rows.
- Tests: each upgradeState renders correctly, enter→preview transition,
  preview→running transition, running→doneOK transition, running→doneError
  transition (with stderr captured), Ctrl-C cancel during running, D from
  preview writes cache and exits mode, Esc from preview exits mode without
  cache write, U key gated on upgradeAvailable.

E2E recommendations: the cold-start auto-check flow and the live-tail

verify the message routing but not the end-to-end "does the user see output

and `internal/ui/upgrade_e2e_test.go` (under the `e2e` build tag, following the
existing convention).

### Regression test (mandatory)

`canopy upgrade` from a DEV binary must continue to refuse cleanly. The new
`--dismiss` flag must NOT bypass that refusal — it's still a DEV refusal case.
Add an explicit regression test for `canopy upgrade --dismiss` on a DEV binary
and assert the existing refusal message is preserved.

## Failure modes

| Codepath | Failure | Response |
|---|---|---|
| `cachedRemoteVersion` | cache file unreadable (permissions) | log at debug, treat as missing; auto-check retries next invocation |
| `cachedRemoteVersion` | cache JSON malformed | log warn, treat as missing, overwrite on next successful fetch |
| `cachedRemoteVersion` | network fetch fails | leave cache unchanged, no pill change; user retries on next invocation |
| `cachedRemoteVersion` | atomic write fails (disk full) | log error, in-memory state still good; next invocation re-fetches |
| `writeUpgradeCheck` | partial write interrupted | atomic tempfile+rename means readers never see partial; on crash, tempfile is orphaned (acceptable, gets overwritten next time) |
| Pill render | `latest_version` malformed (e.g., "abc") | string-equality with current still works; pill renders with whatever string came from upstream (visible diagnostic) |
| `upgradeMode` | CHANGELOG fetch fails (network) | preview state shows "(changelog unavailable, upgrading from vX.Y.Z to vA.B.C)" — flow proceeds, no block |
| `upgradeMode` | `git pull` merge conflict during running | doneError state with full stderr; user runs `cd ~/.canopy/src && git status` per existing message |
| `upgradeMode` | `make install` build error | doneError with last 20 lines of stderr; suggest `cd ~/.canopy/src && make install` to retry manually |
| `upgradeMode` | Ctrl-C during running | context cancels child process; doneError with "canceled" message; cache is NOT rewritten (so the pill stays) |
| `upgradeMode` | TUI window resize during running | safeBuffer keeps producing; renderer wraps based on current width; no special handling required |
| `U` key | pressed when no upgrade available | key not bound (gate on `m.upgradeAvailable()`); silent no-op |
| `D` key | pressed when no upgrade available | key not bound; silent no-op |
| `D` key | pressed during preview, then user changes mind | dismissal is a write — no undo. Acceptable: dismissal is reversible by editing the cache file or by a new release |
| `--dismiss` | called without cached latest | refuse: "no upgrade currently known. Run `canopy upgrade --check` first." |
| `--dismiss` | called on DEV binary | refuse with same message as `canopy upgrade` on DEV |
| Post-upgrade cache rewrite | upgrade succeeded but cache write fails | log warn; next invocation re-fetches and notices we're current; pill disappears one cycle late (acceptable) |
| Auto-check on first run after upgrade | running version > cached latest_version (running ahead of cache) | treat as up-to-date, rewrite cache to match; no pill |

**Critical-gap analysis:** every new failure mode has a test path AND a user-visible
error AND no silent failure modes. The closest to "silent" is the post-upgrade
cache rewrite warn-log case, which degrades to "pill disappears one invocation
late" — visible diagnostic, no data loss, and self-corrects on the next refresh.

## Worktree parallelization strategy

| Step | Modules touched | Depends on |
|------|----------------|------------|
| Commit 1 (cache scaffolding) | `cmd/canopy/` (new file) | — |
| Commit 2 (CLI surfaces) | `cmd/canopy/` (upgrade.go, ls.go) | Commit 1 |
| Commit 3 (pill + wiring) | `internal/ui/`, `cmd/canopy/route.go` | Commit 1 |
| Commit 4 (in-TUI flow) | `internal/ui/` (new file + edits) | Commit 3 |

**Lanes:**
- Lane A: Commit 1 → Commit 2 (sequential, both touch `cmd/canopy/upgrade.go`).
- Lane B: Commit 1 → Commit 3 → Commit 4 (sequential, all in `internal/ui/` after Commit 1).

**Execution order:** Commit 1 lands first (everything depends on it). After 1
merges, Lanes A and B can run in parallel worktrees. Conflict flag: Commit 3
edits `cmd/canopy/route.go` to wire `cachedRemoteVersion` into `RunUnified`;
Commit 2 also edits `cmd/canopy/upgrade.go`. They don't share a file, so the
parallelism is clean.

In practice, given the modest size (each commit is ~150-300 LOC + tests), running
the four commits sequentially is easier than coordinating two worktrees. Recommend
sequential unless there's a reason to parallelize.

## NOT in scope

- **Background daemon.** Rejected per Approach A. Cache-on-disk is the chosen path.
- **Dismissal UI in `canopy ls` plain output.** The hint line says "run
  `canopy upgrade`" — to dismiss, run `canopy upgrade --dismiss`. No second hint.
- **Multi-version dismissal.** Only the latest can be dismissed. If you dismiss
  v0.13 and want to also pre-dismiss v0.14, just dismiss again when v0.14 ships.
- **Time-based snooze (e.g., "remind me in 7 days").** Per-version dismissal
  covers the use case more naturally; timer-based snooze risks nag-loops.
- **Auto-upgrade.** Pill prompts, user acts. Never silent.
- **CHANGELOG search / scrolling.** Preview renders the slice as plain text. If a
  changelog entry is huge, the user sees the head; full doc is on GitHub.
- **Update channels (stable / beta / nightly).** Single channel: `main`. Matches
  source-based install model; no goreleaser feeds to multiplex over.
- **Tmux statusline upgrade indicator.** Considered as a fourth surface; rejected
  to keep tmux statusline focused on workspace state. Re-evaluate if requested.
- **`bubbles/viewport` for streaming.** Reusing `safeBuffer` is sufficient. Adopt
  later if output ever exceeds screen height regularly.
- **`canopy upgrade` standalone TUI.** Folded into the in-TUI flow. The CLI stays
  plain stdout per Approach X.
- **Notification before tmux popup opens.** Pill is the surface; popup users see
  it as soon as the TUI renders. No pre-popup banner.
