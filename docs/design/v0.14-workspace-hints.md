## Problem statement

The TUI's hint column today carries four detector kinds: `rename_suggested`,
`shipped`, `pr_status`, `git_stats`. They cover the "branch needs a name", "PR
state + checks", and "ahead/behind/dirty" axes. With multiple parallel
workspaces in flight, three classes of state still go undetected and bite
users mid-flight:

1. **Mergeability.** You can't tell from the row whether `git merge main` (or
   the equivalent rebase) would conflict. You discover this at /ship time.
2. **Stuck git state.** A workspace mid-rebase, mid-merge, or with detached
   HEAD looks identical to a healthy one. You context-switch back days later
   and tail-spin into "wait, why is my next commit weird."
3. **Push state.** `↑N` today means "ahead of main." It does NOT mean
   "ahead of origin/&lt;branch&gt;." Those answers diverge constantly during
   parallel work, and the question users actually ask 20× a day is *"is my
   work backed up on origin?"*

The narrow goal: expand the hint vocabulary to cover these three classes with
detectors that are cheap, parallel-safe, and rendered with restraint so the
hint row doesn't become a Christmas tree.

## What makes this cool

You're scanning the Global tab across five canopy workspaces. One row jumps
out: `feat-billing  ⚠ conflict  ↑3 ↓2 *1`. You haven't started shipping, you
haven't fetched main today, but canopy already knows: if you tried to merge,
it would explode. You fix it before /ship time. Two rows down:
`refactor-auth  ⚠ rebasing` in bold orange. You forgot you'd left it
mid-rebase three days ago. One glance and you know what state every
workspace is in.

## Constraints

- **Parallel-safe detector model.** New detectors plug into the existing
  `RunFast` goroutine pool. No detector blocks others; failures are silent
  (return nil, defer to next refresh).
- **Local cost budget.** All Lane 1 detectors stay under ~100ms wall clock
  on typical worktrees. Network-backed signals (gh) reuse the existing 10min
  cache pattern.
- **Single-row badges.** The hint column is one TUI line. Render rules
  must keep the worst case under ~60 visible cols. Loud (orange/bold)
  badges preempt informational (grey) ones when the row is full.
- **No state file (this revision).** Detectors stay pure. PR-comment-unread
  and other "last-seen" tracking are deferred to a follow-up PR that owns
  the state file design.

## Scope: three lanes, ship Lane A in this PR

The eng review identified three independent lanes. This PR ships Lane A
only — full code path including detector, wiring, badge rendering, and
tests. Lanes B and C are scheduled for parallel workspaces and arrive
behind their own PRs.

```
Lane A — mergeability       THIS PR        ⚠ conflict
Lane B — stuck_state        next workspace ⚠ rebasing / ⚠ merging / ⚠ detached
Lane C — push_state         next workspace ⇡N (unpushed) / ⇅ (diverged)
```

Lanes B/C touch only `internal/lifecycle/` plus the badge precedence list
in `projectlist.go`, so they parallelize cleanly. The only file all three
lanes touch is `detect.go` (one-line entry per goroutine) and
`projectlist.go` (one switch case per badge). Conflicts there are trivial
to resolve at merge time.

## Premises

1. **`git merge-tree --write-tree` (git 2.38+) is the right primitive.**
   It simulates the merge in the object store without touching the working
   tree or index. Exit code 1 = conflicts; output (with `--name-only`)
   begins with the merged tree OID followed by conflicted paths. No
   working-tree side effect, no need to stash or restore. ~30-80ms on
   typical worktrees.

2. **Short-circuit when target is fully merged.** If `origin/&lt;default&gt;` is
   an ancestor of HEAD (i.e., main has nothing the branch doesn't already
   have), no merge is needed and no conflicts are possible. Skip the
   `merge-tree` call. Cheap `merge-base --is-ancestor` check first.

3. **Silent failure on old git.** If `merge-tree --write-tree` is
   unrecognized (git &lt;2.38), the detector returns nil. We do not warn or
   degrade. The user simply doesn't get the hint. Coverage is fine: git
   2.38 shipped in 2022 and `--write-tree` was the modern-merge default
   well before 2026.

4. **One hint per detector per refresh.** Mirrors the existing pattern.
   The hint message is what the badge renders, formatted by the detector.

5. **Mergeability does NOT preempt git_stats.** Both convey relevant
   info about the same axis (divergence from main). Render mergeability
   in a loud orange between rename and git_stats. The user wants to see
   `⚠ conflict ↑3 ↓2` together — the conflict warning AND the count of
   what's diverged.

## Architecture

### Detector

`internal/lifecycle/mergeability.go`

```
detectMergeability(ctx, ws) -&gt; *state.Hint
  ws.Path empty                                          -&gt; nil
  gitDefaultBranch fails                                 -&gt; nil
  origin/&lt;default&gt; AND &lt;default&gt; both missing            -&gt; nil
  target is ancestor of HEAD (no merge needed)           -&gt; nil
  git merge-tree --write-tree --name-only HEAD target
    exit 0  (clean merge)                                -&gt; nil
    exit 1  (conflicts)                                  -&gt; Hint
    exit 2+ (error / unsupported)                        -&gt; nil
```

Hint shape:

```go
state.Hint{
    Kind:       "mergeability",
    Message:    "⚠ conflict"  | "⚠ N conflicts",
    Action:     "git fetch origin &amp;&amp; git rebase origin/&lt;default&gt;",
    DetectedAt: time.Now(),
}
```

### Wiring (`detect.go`)

```
detectorCount: 4 -&gt; 5
+ goroutine launching detectMergeability and pushing into the results chan
```

No reordering of existing detectors.

### Badge rendering (`projectlist.go`)

Insert between rename and git_stats:

```
parts order:
  rename_suggested      ↻ rename
  mergeability          ⚠ conflict        (NEW, orange, attention)
  git_stats             ↑N ↓N *N          (grey)
  pr_status / shipped   PR open · checks  (color per state)
```

Color: same orange as `hintRenameStyle()` (already used for "PR changes" and
failing checks). Stays inside the existing palette.

### Cost / cadence

| Path                          | Mechanism                                  | Cost      |
|-------------------------------|---------------------------------------------|-----------|
| Empty workspace path          | early return                                | free      |
| Resolve default branch        | git symbolic-ref / config (cached by git)   | &lt;5ms      |
| Ref existence                 | git rev-parse --verify                      | &lt;5ms      |
| Ancestor short-circuit        | git merge-base --is-ancestor                | ~10ms     |
| Conflict simulation (cold)    | git merge-tree --write-tree --name-only     | 30-80ms   |

In steady state for synced workspaces (target is ancestor of HEAD), the
ancestor short-circuit kicks in and we never call merge-tree. So the
amortized cost during normal work is closer to ~15ms per refresh per
workspace. Worst case (every workspace diverged from main) stays
parallel-bounded inside `RunFast`'s goroutine pool — wall time stays
near ~80ms regardless of N workspaces.

### Failure modes

| Failure                                          | Impact                  | Mitigation                                |
|--------------------------------------------------|-------------------------|-------------------------------------------|
| git &lt; 2.38 (--write-tree unsupported)            | nil hint                | accepted; silent fallback                 |
| origin/main not fetched                          | falls back to local main| handled (existing pattern from git_stats) |
| huge tree, slow merge-tree                       | up to ctx timeout       | runs inside RunFast goroutine; bounded    |
| merge-tree creates orphan tree objects           | object-store growth     | accepted; gc reaps eventually             |
| .git is a file (worktree gitdir pointer)         | works (git resolves it) | no extra handling needed                  |

### Test plan

`internal/lifecycle/mergeability_test.go`:

- `TestFormatMergeability` — singular vs plural rendering.
- `TestDetectMergeability_Clean` — fresh worktree, nothing diverged, returns nil.
- `TestDetectMergeability_NoConflictDivergence` — branch and main diverge but
  on different files, returns nil (clean merge).
- `TestDetectMergeability_Conflict` — branch and main edit same file with
  different content, returns Hint with Kind="mergeability" and "conflict" in
  Message and "rebase" in Action.

`internal/ui/projectlist/projectlist_test.go`:

- `TestRender_MergeabilityBadge` — Hint{Kind:"mergeability", Message:"⚠ conflict"}
  renders the badge in the right position relative to rename and git_stats.
- `TestRender_MergeabilityBadge_AlongsideGitStats` — both badges visible
  together; mergeability does not preempt git_stats.

All tests run via `go test ./...` (no -tags=e2e gating; pure stdlib + git).

## Worktree parallelization plan

```
Lane A: mergeability.go + tests + detect.go entry + projectlist badge case
        (THIS PR)

Lane B (next workspace, parallelizable):
        stuck_state.go + tests + detect.go entry + projectlist badge case

Lane C (next workspace, parallelizable):
        push_state.go + tests + detect.go entry + projectlist badge case
```

Lanes B and C share two files with Lane A: `detect.go` (one-line entries
in the parallel goroutine block) and `projectlist.go` (one switch case
in `RenderHintBadges`). These are mechanical merges — each lane appends
its own goroutine and its own badge case. Trivial three-way merge.

Once all three lanes land, a follow-up render-precedence pass will:

- Compose stuck_state to preempt git_stats (mid-rebase rows shouldn't show
  ↑3 ↓1 *5 alongside the rebase warning).
- Add width-aware truncation for the global view.

That precedence pass owns no detector logic; it's a pure render-layer
refinement and ships separately so each lane stays small.

## NOT in scope (this PR)

- Stuck-state detection (Lane B, separate workspace)
- Push-state separation from git_stats (Lane C, separate workspace)
- Render-precedence overhaul (after all three lanes land)
- Cross-workspace file-overlap detection
- Lockfile drift, submodule state, draft-PR-as-its-own-badge

## What already exists (and we reuse)

- `internal/lifecycle/RunFast` — parallel detector dispatch, results
  aggregation. We add one more goroutine.
- `gitDefaultBranch`, `gitRefExists` — already factored out in
  `rename.go`/`shipped.go`. Mergeability reuses them.
- `state.Hint` — single struct used for all detector outputs. Adding a
  new Kind requires no schema changes.
- `RenderHintBadges` — single render switch in `projectlist.go`. Adding
  a new badge means one new style helper plus one switch case.
- `lipgloss` palette — orange (`hintRenameStyle`) already used for
  attention badges. We reuse it.
