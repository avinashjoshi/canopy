# Design: Agent lifecycle wrapper

Status: Draft, captured 2026-04-28 after `ancient-hornet` shipped.
Pairs with: TODOS.md "v0.6 — Agent lifecycle wrapper" (umbrella entry) +
"v0.5 — Multi-AI-tool support" (foundation, already specced).

## Problem statement

Today canopy spawns the agent pane with a hardcoded `claude --continue || claude`.
This locks canopy to Claude Code, and even within Claude there's no way for canopy
to inject context about the workspace (its name, branch, port, the lifecycle
conventions) into the agent's system prompt. The user has to remember:

- Rename the auto-generated branch (`ancient-hornet`) to something intent-based
  (`open-canopy-anywhere`) once the feature is scoped.
- Run `canopy rm <workspace>` after the PR merges so the worktree, tmux session,
  and state row are cleaned up.

Both of these steps want to be agent-driven — Claude (or any other coding agent)
is already in the loop, knows the feature's intent, and can do the bookkeeping
once it sees the conventions. But there's no agent-agnostic way to pass canopy's
conventions into the agent's prompt, and no canopy verb for the rename step.

The user's stated direction (2026-04-28): "Wrap everything together as a
'system prompt kinda' before we start the agent session. Should work with
Claude AND eventually Codex / OpenCode."

## What Makes This Cool

- **Agent-agnostic.** canopy assembles workspace context once. Each agent has
  a tiny adapter that knows how to feed that context into its own system-prompt
  surface. Switching agents per-project = changing one config string.
- **Lifecycle becomes ambient.** Every agent session that boots inside a canopy
  workspace knows it's in one, knows what to do at scope-time and ship-time.
  No CLAUDE.md sprinkles needed across N projects.
- **One canonical "where canopy ends, agent begins" boundary.** The `scripts.agent`
  hook is to the agent pane what `scripts.run` is to the dev-server pane —
  user-supplied, canopy-invoked, env-var-fed.

## Constraints

- **Backwards compatible.** Existing canopy.json files without `scripts.agent`
  must continue to spawn `claude --continue || claude` exactly as today.
- **No agent SDK dependency.** canopy stays pure stdlib + os/exec. We don't
  link against any agent's Go bindings.
- **Workspace name is immutable.** Renaming the tmux session or worktree dir
  mid-flight breaks tmux's attach plumbing and any background processes that
  cache `CANOPY_WORKSPACE_PATH`. Only the git branch is renameable.
- **Trigger for cleanup is fuzzy.** "PR merged into main" is the natural signal,
  but canopy doesn't watch GitHub. v0.6 keeps cleanup explicit (Claude calls
  `canopy rm`); auto-trigger is a v1+ stretch.

## Approaches considered

### A: CLAUDE.md per-repo conventions (status-quo extension)

Add a `## Workspace lifecycle` section to each project's CLAUDE.md describing
the rename + rm workflow. Other agents need their own equivalent (AGENTS.md
for OpenCode, .codexrc for Codex, etc.).

**Reject.** Doesn't unify across agents. Drift across files. Doesn't help
canopy ship a curated default.

### B: One built-in briefing canopy injects directly (no user config)

canopy hardcodes a "you're in workspace X, branch Y, run rename / rm, ..." prompt
and uses agent-specific flags (`claude --append-system-prompt`, etc.) to inject
it. No `scripts.agent` hook.

**Reject.** Forces canopy to know about every agent's prompt-injection mechanism,
which hardcodes the same coupling we're trying to break.

### C: `scripts.agent` + canopy-assembled briefing file (CHOSEN)

canopy writes `<workspace>/.canopy/AGENT.md` at workspace-create time. The user
provides `scripts.agent` (a small launcher script). canopy spawns that script
in the agent pane. The script is responsible for one thing: feed the contents
of `.canopy/AGENT.md` into the user's chosen agent.

```
canopy.json:
  scripts.agent  →  bin/canopy-agent          (user-written, ~5 lines)
  agent_briefing →  "Use Rails 7 conventions" (optional, project-specific)

canopy create-time:
  writes .canopy/AGENT.md with:
    - Workspace context (name, branch, port, root path, tmux session)
    - Universal lifecycle reminders (rename, ship, rm)
    - + project's agent_briefing (appended verbatim)

canopy spawns agent pane:
  bin/canopy-agent .canopy/AGENT.md
  └─ user's script invokes their chosen agent with the briefing:
     - Claude Code:  claude --append-system-prompt "$(cat $1)"
     - OpenCode:     cp "$1" AGENTS.md && opencode
     - Codex:        codex --system-prompt-file "$1"
     - aider:        aider --message-file "$1"
```

**Why C wins:** canopy stays agent-agnostic. The user (or canopy's `--with-scripts`
scaffold) writes a 5-line bash script that adapts to whatever agent that project
uses. New agents get added by writing a new launcher template, not by changing
canopy.

## Architecture

### Three pieces

```
┌──────────────────────────────────────────────────────────────────┐
│  1.  canopy.json schema additions                                │
│                                                                  │
│      scripts.agent      string  (path to launcher; optional)     │
│      agent_briefing     string  (free-text, optional)            │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│  2.  workspace.Create writes .canopy/AGENT.md                    │
│                                                                  │
│      Template engine: text/template (stdlib).                    │
│      Inputs:                                                     │
│        - state.Workspace (Name, Branch, Port, Path, TmuxSession) │
│        - cfg.ProjectRoot                                         │
│        - cfg.AgentBriefing                                       │
│        - canopy version (from runtime/debug.ReadBuildInfo)       │
│      Output: <workspace>/.canopy/AGENT.md                        │
│                                                                  │
│      The template lives in canopy as a const string. Universal   │
│      lifecycle reminders are baked in; per-project text is       │
│      appended after.                                             │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│  3.  Agent pane invocation                                       │
│                                                                  │
│      buildSession(): if cfg.Scripts.Agent != "":                 │
│        spawn `bin/canopy-agent .canopy/AGENT.md`                 │
│      else:                                                       │
│        spawn today's `claude --continue || claude`               │
│                                                                  │
│      CANOPY_AGENT_BRIEFING_PATH is also set in the pane's env    │
│      so the script can find the briefing without a positional    │
│      argument if it prefers.                                     │
└──────────────────────────────────────────────────────────────────┘
```

### `.canopy/AGENT.md` template (sketch)

```markdown
# Canopy workspace context

You are working inside a canopy workspace — an isolated git worktree paired
with its own tmux session and dev-server port. Canopy assembles this file
at workspace-create time so any coding agent (Claude, Codex, OpenCode, aider,
...) has the same starting context.

## This workspace

- **Workspace name:** {{.Workspace.Name}}
- **Branch:** {{.Workspace.Branch}}
- **Source repo:** {{.ProjectRoot}}
- **Worktree dir:** {{.Workspace.Path}}
- **Port:** {{.Workspace.Port}}
- **Tmux session:** {{.Workspace.TmuxSession}}

## Workspace lifecycle (canopy conventions)

1. **Scope.** Once you understand the feature's intent, run
   `canopy rename <intent-name>` from the **outer** terminal (canopy refuses to
   run from inside its own tmux sessions). Example:
   `canopy rename open-canopy-anywhere`. This renames the git branch only;
   the workspace dir + tmux session keep their generated name.

2. **Develop.** Work normally. Don't run `canopy <subcommand>` from inside
   this tmux session — it's blocked by the tmux-nesting guard. Use the outer
   terminal, or use the in-session overlay (TODOS.md v1) once it ships.

3. **Ship.** Use the project's usual ship workflow. For gstack users that's
   `/ship`; for others it's whatever PR/merge process the project follows.

4. **Clean up.** After the PR merges into main, run `canopy rm {{.Workspace.Name}}`
   from the outer terminal to tear down this workspace. That removes the tmux
   session, deletes the git worktree + branch, and drops the state row.

{{if .AgentBriefing}}
## Project briefing

{{.AgentBriefing}}
{{end}}

---

This file is regenerated by `canopy new`. Edit `agent_briefing` in
canopy.json to change the per-project portion.
```

### `scripts.agent` default templates (canopy ships these as `--with-scripts` scaffolds)

**Claude Code** (most common, the v0 default):

```bash
#!/usr/bin/env bash
# canopy agent: launches the project's coding agent in the agent tmux pane
# with the canopy-assembled briefing as the system prompt.
set -euo pipefail
BRIEFING="${CANOPY_AGENT_BRIEFING_PATH:-.canopy/AGENT.md}"
cd "${CANOPY_WORKSPACE_PATH}"
# --continue resumes per-directory chat history if any; falls back to fresh.
exec claude --append-system-prompt "$(cat "$BRIEFING")" --continue 2>/dev/null \
  || exec claude --append-system-prompt "$(cat "$BRIEFING")"
```

**OpenCode** (uses AGENTS.md natively):

```bash
#!/usr/bin/env bash
set -euo pipefail
BRIEFING="${CANOPY_AGENT_BRIEFING_PATH:-.canopy/AGENT.md}"
cd "${CANOPY_WORKSPACE_PATH}"
# OpenCode reads AGENTS.md from the project root; symlink ours in.
ln -sf "$BRIEFING" AGENTS.md
exec opencode
```

**Codex** (TBD — depends on which Codex CLI variant; placeholder):

```bash
#!/usr/bin/env bash
set -euo pipefail
BRIEFING="${CANOPY_AGENT_BRIEFING_PATH:-.canopy/AGENT.md}"
cd "${CANOPY_WORKSPACE_PATH}"
exec codex --system-prompt-file "$BRIEFING"
```

These templates ship in `cmd/canopy/init.go`'s scaffold registry and are
selected by a flag: `canopy init --with-scripts --agent claude` (default)
or `--agent opencode|codex|aider`.

### `canopy rename <new-name>` verb

```
canopy rename <new-branch-name>
```

Pre-conditions (all checked under state.WithLock):
- cwd is inside a canopy workspace (resolved via cfg.ProjectRoot + state lookup)
- `<new-branch-name>` doesn't already exist as a branch in the source repo
- `<new-branch-name>` passes `git check-ref-format --branch`

Atomic operation:
1. `git -C <source-repo> branch -m <old> <new>`
2. Update `state.Workspaces[i].Branch = new` for the matching row.
3. Save state.

Workspace dir name + tmux session name are NOT changed (mid-flight rename of
those fields breaks tmux attach + invalidates `CANOPY_WORKSPACE_PATH` for any
running scripts).

Idempotency: if old == new, exit 0 with a friendly "nothing to do" message.

Error cases (all surface clean errors, no partial mutations):
- Branch name already exists → "branch X already exists; pick a different name"
- Workspace not found in state → "no canopy workspace at cwd"
- Not inside a canopy workspace → "not inside a canopy workspace; cd into one first"

### Lifecycle workflow (the full loop)

```
┌────────────────┐
│ canopy new     │  user runs in source repo
└──────┬─────────┘
       │  generates "ancient-hornet"; runs scripts.setup;
       │  writes .canopy/AGENT.md; spawns scripts.agent in agent pane
       ▼
┌────────────────┐
│ Agent boots    │  reads .canopy/AGENT.md; knows lifecycle conventions
└──────┬─────────┘
       │
       │  -- agent + user collaborate to scope the feature --
       │
       ▼
┌────────────────┐
│ canopy rename  │  agent (or user) runs in outer terminal
│ <intent-name>  │  e.g. canopy rename open-canopy-anywhere
└──────┬─────────┘
       │  git branch -m + state.Branch update
       ▼
┌────────────────┐
│  develop       │  normal work; PR; review; ship
└──────┬─────────┘
       │
       ▼
┌────────────────┐
│  PR merges     │  on main
└──────┬─────────┘
       │  agent (or user) runs in outer terminal:
       ▼
┌────────────────┐
│ canopy rm      │  tears down: archive script, tmux kill,
│ ancient-hornet │  worktree remove, branch delete, state drop
└────────────────┘
```

The agent's system prompt (from `.canopy/AGENT.md`) tells it about steps 2 and
4 explicitly, so any agent that follows its system prompt drives the lifecycle
naturally without project-specific CLAUDE.md sprinkles.

## Schema additions (canopy.json)

```json
{
  "scripts": {
    "setup":   "bin/canopy-setup",
    "run":     "bin/dev",
    "archive": "bin/canopy-archive",
    "agent":   "bin/canopy-agent"
  },
  "agent_briefing": "This is a Rails 7 app. RSpec for tests, Standard for linting. Touch nothing under app/legacy/."
}
```

Backwards compat: empty `scripts.agent` → today's hardcoded `claude --continue || claude`.

## State machine impact

None. State.Workspace gets a Branch-field update path (already in
`canopy rename`), but no schema additions. `.canopy/AGENT.md` lives in the
worktree, not in state.json.

## Test plan

### `canopy rename`
- Happy path: existing workspace, new branch name doesn't exist → branch
  renamed, state row's Branch updated, exit 0.
- Idempotent: rename to current name → "nothing to do", state unchanged.
- Branch name conflict: target already exists → ErrBranchExists, no mutation.
- Invalid branch name: fails `git check-ref-format` → clean error, no mutation.
- Not in workspace: cwd is source repo → ErrWorkspaceNotFound.

### `.canopy/AGENT.md` generation
- Template renders all workspace fields correctly.
- `agent_briefing` empty → section omitted.
- `agent_briefing` populated → appended verbatim, including newlines.
- File is written before scripts.agent spawns (ordering test in workspace.Create).
- File survives `canopy retry` (regenerated, not preserved).

### `scripts.agent` invocation
- E2E: a fixture script that just `cat`s its $1 into a known file.
  Verify the agent pane invokes it with the right path and the right env vars.
- Backwards compat: empty `scripts.agent` → claude (or fallback) is spawned
  exactly as today.

## Distribution-side concerns

- `canopy init --with-scripts` grows an `--agent <name>` flag that picks the
  right `bin/canopy-agent` template (claude / opencode / codex / aider).
  Default: claude.
- README adds an "Agent compatibility matrix" table mirroring TODOS.md's
  existing notes (Claude full magic, aider full magic, codex degraded, etc.).
- `docs/canopy-json.md` documents both new fields.

## Open questions

1. **Auto-cleanup trigger.** v0.6 keeps `canopy rm` explicit. v1 could watch
   the source repo for branch deletion (`git fetch --prune` + check) and
   auto-rm orphaned workspaces. Hard part is "is it really merged or is the
   user just renaming?" Probably needs a confirmation step.

2. **Briefing freshness.** If the user edits `agent_briefing` in canopy.json
   AFTER workspace creation, the workspace's `.canopy/AGENT.md` is stale.
   Options: (a) regenerate on every attach, (b) add `canopy refresh-briefing`
   verb, (c) accept staleness — briefing applies to new workspaces only.
   Lean toward (c) for v0.6, revisit if it bites.

3. **What about `scripts.agent` when nvim or shell panes spawn?** Today canopy
   spawns three panes: nvim, claude, $SHELL. The `scripts.agent` proposal
   replaces the claude pane. Nvim and shell stay hardcoded. Is that the right
   factoring, or should ALL pane commands go through configuration? Out of
   scope here — the layout-as-config TODOS.md entry covers that. This design
   only opens the agent pane.

4. **Multi-agent within one workspace.** Already captured in TODOS.md as a v1
   feature ("Multi-AI within one workspace"). This design doesn't preclude it
   — the second agent pane would invoke a different `scripts.agent`-shaped
   script. Defer.

## Success criteria

- A user can switch from Claude to OpenCode by editing `scripts.agent` in
  canopy.json. No canopy code change needed.
- A new agent session that boots inside a canopy workspace knows about the
  rename + rm conventions without reading any project-specific CLAUDE.md.
- `canopy rename intent-name` is one command and works without breaking the
  attached tmux session.
- Backwards compatible: existing canopy.json files keep working without edits.
