## Problem statement

Two pain points, one root cause.

**Dev pain.** Switching between the released canopy and an in-flight dev build is friction-heavy:
- `~/.local/bin/canopy` is whatever was last `make install`ed
- `./canopy` lives in a worktree
- `~/.tmux.conf` bakes the *absolute path* of whichever binary ran `canopy install tmux`, so swapping binaries means re-running install-tmux every time
- With multiple parallel feature worktrees (each with its own `./canopy` build), there's no way to spin one up, then another, then back to released, without manual symlink dancing or rebuild-from-main

**End-user pain.** There is no install path other than "git clone + make install." No published binaries, no curl-able installer, no `canopy upgrade`. Users updating canopy have to remember the source path, cd into it, git pull, make install. End users don't exist yet because there's no way for them to start.

The unifying root cause: canopy doesn't have a stable `canopy` name on PATH that points at the active binary, and the surrounding install/upgrade conventions haven't been built. The tmux path-baking is a downstream symptom of that.

## What makes this cool

`canopy use feature-A`, `canopy use feature-B`, `canopy use release` — each one a millisecond symlink flip with no rebuild. Status bar instantly reflects which canopy you're driving. Tmux popup follows automatically. Multiple Claudes in parallel worktrees keep testing against their own `/tmp/canopy-XX` binaries, undisturbed.

For end users: `curl -fsSL https://raw.githubusercontent.com/oncactus/canopy/main/install.sh | sh` and you're running canopy. `canopy upgrade` keeps you current. Same shape as gstack, gbrain — consistent ergonomics across the dogfooding stack.

## Constraints

- **Distribution model:** source-based, mirroring gstack/gbrain. No binary releases for v1. Audience is devs comfortable with shells; they have or can install Go.
- **Required prereqs:** git 2.x+, tmux 3.2+, Go 1.22+.
- **Expected (not enforced):** Claude Code, Neovim — assumed by canopy.json defaults but not runtime requirements.
- **No goreleaser, no GitHub Releases, no semver tags load-bearing.** Tags optional, decorative.
- **Backward-compatible Makefile:** existing `make install` / `make build` continue working with same semantics, gain a symlink layer.
- **Single user state for the active binary.** One global symlink `~/.local/bin/canopy`, one switching primitive (`canopy use`).

## Premises (locked)

1. **Source-based, not binary-based.** Match gstack/gbrain. End users build from source on install. `canopy upgrade` runs `git pull && make install` in the source clone.
2. **`~/.canopy/src` is the canonical source location.** Lives alongside `~/.canopy/workspaces/` and `~/.canopy/log/` — symmetric with how canopy already organizes itself.
3. **`~/.local/bin/canopy` is a symlink, never a binary.** Target is `canopy.bin` (release) or a worktree's `./canopy` (dev). Switching = retargeting the symlink.
4. **Tmux config invokes bare `canopy` (PATH-resolved), not an absolute path.** This is the fix that makes binary swapping invisible to tmux integration.
5. **Visual indication is non-negotiable.** TUI status bar, tmux statusline segment, and `canopy version` all surface "release vs DEV, and which workspace if dev" at three levels of detail.
6. **Parallel Claudes test against per-worktree binaries (`./canopy` or `/tmp/canopy-XX`), never bare `canopy`.** Global symlink belongs to user state. Codified in CLAUDE.md so all future Claudes inherit the rule.
7. **Tagging is optional.** When the user wants a CHANGELOG snapshot or a "known-good marker," cut a tag. No automation depends on tags.

## Architecture

### Filesystem shape

```
~/.canopy/
  src/                              ← source clone (managed by install.sh + canopy upgrade)
  workspaces/canopy/<name>/         ← existing worktrees with their own ./canopy builds
  log/                              ← existing logs
  state.json                        ← existing registry

~/.local/bin/
  canopy.bin                        ← compiled release binary (from `make install` on main)
  canopy → canopy.bin               ← symlink. The active canopy. Flipped by `canopy use`.

~/.tmux.conf
  # canopy:start ... bind g display-popup -E ... "canopy"  ← bare, PATH-resolved
  # canopy:end
```

### Switching state machine

```
                    ┌─────────────────────────────────────┐
                    │      canopy → canopy.bin            │
                    │      (release, gray "v0.12.0")      │
                    │                                     │
                    └──┬──────────────────────────────┬───┘
                       │                              │
                       │ canopy use feature-A         │ canopy use release
                       │ (or `make dev` in A)         │ (or `make release` anywhere)
                       ▼                              │
                    ┌─────────────────────────────────┼───┐
                    │  canopy → ~/.canopy/.../A/canopy│   │
                    │  (DEV, cyan "DEV: feature-A")   │   │
                    │                                 │   │
                    └──┬──────────────────────────┬───┴───┘
                       │                          │
                       │ canopy use feature-B     │
                       ▼                          │
                    ┌──────────────────────────┐  │
                    │ canopy → .../B/canopy    │──┘
                    │ (DEV, cyan "DEV:B")      │
                    └──────────────────────────┘
```

All transitions are atomic `os.Rename` over a tempfile-symlink, no rebuild during switching. Released `canopy.bin` only ever rebuilt by explicit `make install` on main (existing convention preserved).

### Install + upgrade flow

```
END-USER FIRST INSTALL
  curl raw.githubusercontent.com/.../install.sh | sh
    ├── detect OS (uname -s, uname -m)
    ├── check prereqs: git, tmux >=3.2, Go >=1.22
    │     missing? → print exact `apt`/`brew` install line, exit 1
    ├── git clone https://github.com/oncactus/canopy.git ~/.canopy/src
    ├── cd ~/.canopy/src && make install
    │     → builds canopy.bin, symlinks ~/.local/bin/canopy → canopy.bin
    └── PATH hint if ~/.local/bin not on PATH

END-USER UPGRADE
  canopy upgrade
    ├── refuse if running from a DEV binary (clear message)
    ├── curl https://raw.githubusercontent.com/oncactus/canopy/main/VERSION
    ├── compare with running version → up-to-date? exit 0
    ├── print CHANGELOG.md diff (sections newer than running version)
    ├── git -C ~/.canopy/src pull --ff-only
    └── make install in ~/.canopy/src

DEV-LOOP UPGRADE (you, on main)
  cd ~/Work/canopy && git pull && make install
    → unchanged from today's convention
```

### Version resolution

```
make build          → ldflags inject `version = main-<short-sha>` from git
make install        → ldflags same as build, plus symlink mgmt
make dev            → no ldflags, version stays "dev" → triggers DEV mode
canopy upgrade      → builds via `make install`, gets `main-<sha>` from VERSION + git
go install ...      → no ldflags, version stays "dev", BuildInfo fallback to pseudo-version

canopy version detection:
  if version == "dev" → DEV mode, look up workspace by binary path
  else                → release mode, show version + commit
```

### `canopy use` subcommand

```
canopy use                       Show current target + list available
canopy use release               Symlink → canopy.bin (alias: `main`)
canopy use <workspace-name>      Symlink → ~/.canopy/workspaces/canopy/<name>/canopy
canopy use --build <workspace>   go build in that worktree, then switch
```

Listing format:
```
Active: ~/.local/bin/canopy -> canopy.bin (main-abc1234, release)

Available targets:
  release                    canopy.bin                  main-abc1234   built 2h ago
  install-and-dev-workflow   ~/.canopy/.../canopy        dev            built 5m ago
  popup-keybind-tweaks       ~/.canopy/.../canopy        dev            built 12h ago  ← stale
  config-reload              (not built)                                run `make build` first
```

Stale detection: `./canopy` mtime older than the worktree HEAD commit time.

Implementation: walks `~/.canopy/workspaces/canopy/*` directories, opens each as a git worktree to read HEAD time, stats `./canopy`. ~80 lines + tests.

### Visual indicators

**TUI status bar (corner of every screen, lipgloss-styled):**
- Release: `v0.12.0` muted gray
- Dev: `DEV: <workspace-name>` cyan

Detection: `version == "dev"` → DEV. Workspace lookup: `git -C $(dirname $(os.Executable())) branch --show-current`.

**Tmux statusline segment** (`canopy statusline --format=current`, runs every status interval):
- Release: `[ canopy:install-and-dev-workflow ]`
- Dev: `[ canopy:install-and-dev-workflow [DEV:install-and-dev-workflow] ]`

Append the `[DEV:branch]` suffix only when the running canopy is itself a dev build (regardless of which workspace's tmux you're in).

**`canopy version` (forensic detail):**

Release:
```
canopy v0.12.0
  commit:  abc1234
  built:   2026-04-30T12:34:56Z
  binary:  /home/avi/.local/bin/canopy -> canopy.bin
  mode:    release
```

Dev:
```
canopy DEV
  workspace: install-and-dev-workflow
  binary:    ~/.local/bin/canopy -> ~/.canopy/.../canopy
  commit:    abc1234 (dirty)
  mode:      DEV
```

## Approaches considered

### Approach A: goreleaser + tags + GH Releases (REJECTED)
Standard Go CLI distribution. Cross-compiled binaries hosted as GitHub Releases per tag. Users curl|sh, `canopy upgrade` hits the GH API. Solid pattern (gh, fly, k9s all do this), but adds `.goreleaser.yaml`, `release.yml`, signed binaries (or Gatekeeper warnings on Mac), and a tag/release ceremony every time. ~80 extra lines of config, 4 cross-built artifacts per release, Gatekeeper friction, mismatched mental model with gstack/gbrain. Solves a problem (binary distribution) the audience doesn't have.

### Approach B: Rolling release via goreleaser (REJECTED)
Same as A but no semver tags — a single force-updated `rolling` GH Release. Trades tag ceremony for force-push gymnastics on a moving tag. Awkward for `go install` users (pseudo-versions), awkward rollback story, and still requires goreleaser config. Worst of both worlds once we realized source-based was viable.

### Approach C: Source-based (CHOSEN)
Match gstack/gbrain. `install.sh` clones, `make install` builds, `canopy upgrade` git-pulls. VERSION file + raw.githubusercontent for update checks. Tags optional. Audience already has Go.

**Why C wins:** simpler (no goreleaser config, no release workflow, no Gatekeeper, no cross-compile matrix), consistent with the rest of the user's tooling, matches the user's existing dogfood habit ("make install after every main commit" = exactly the source-based upgrade flow), and degrades gracefully — if non-Go users ever materialize, A layers on top without replacing C.

### Sub-decisions within the chosen approach

- **Symlink switching vs env-var override vs explicit subcommand only.** Picked symlink + `canopy use` subcommand. Symlink because it's a Unix primitive everyone understands; subcommand because canopy already knows where workspaces live and the user wants to switch from anywhere.
- **`canopy use` vs Makefile targets.** Both. Subcommand is the source of truth, Makefile targets (`make dev`, `make release`) are thin wrappers for muscle memory.
- **Bare `canopy` in tmux config vs explicit path.** Bare. The whole point of the symlink is that everything follows it transparently.

## Implementation plan

Single PR, four logical commits.

### Commit 1: Tmux bare-canopy fix
Smallest, lowest-risk, ship-able alone.
- `cmd/canopy/install_tmux.go`: `canopyBinForBlock()` returns `"canopy"` unconditionally. Drop `os.Executable()` resolution. Update docstring.
- `cmd/canopy/install_tmux_test.go`: rebaseline existing tests; add regression test asserting the block contains `canopy` and **does not** contain an absolute path.

### Commit 2: Makefile + version banner + visual indicators
- `Makefile`: install to `~/.local/bin/canopy.bin`, symlink `canopy → canopy.bin`. Inject ldflags from `VERSION` + `git rev-parse --short HEAD` so `make install` produces `main-<sha>` not `dev`. Add `make dev` and `make release` Makefile targets (which Commit 3 will refactor to call `canopy use`).
- `VERSION`: new file at repo root containing the current version (e.g. `0.12.0`).
- `cmd/canopy/main.go`: enhance `versionCmd` output to include resolved binary path, mode, and workspace name when in DEV. Workspace resolution = `git -C <binary-dir> branch --show-current`.
- `cmd/canopy/statusline.go`: extend `--format=current` to append `[DEV:<branch>]` when running canopy is dev.
- `cmd/canopy/statusline_test.go`: cover the new DEV suffix branch.
- `internal/ui/...`: add a single-line status indicator to the TUI footer/header (lipgloss). Release = muted gray version, Dev = cyan `DEV: <workspace>`.
- `internal/ui/..._test.go`: render test for both states using a `*Model` literal as the existing pattern.

### Commit 3: `canopy use` subcommand + CLAUDE.md update
- `cmd/canopy/use.go` (new): list/switch/--build modes. Atomic symlink replace via `os.Rename` over a tempfile in `~/.local/bin`. Walks `~/.canopy/workspaces/canopy/*` to enumerate dev targets. Stale detection by mtime vs HEAD time. `Annotations: allowInTmuxAnnotation: true` so it works from inside any canopy session.
- `cmd/canopy/use_test.go` (new): missing release binary, missing dev binary, unknown workspace name, atomic flip, stale detection, `--build` happy path. Use `t.TempDir()` for filesystem fixtures.
- `Makefile`: refactor `make dev` and `make release` into thin wrappers calling `canopy use $(basename $(git rev-parse --show-toplevel))` and `canopy use release` respectively.
- `CLAUDE.md`: add **Multi-workspace dogfooding** section instructing future Claudes to use `./canopy` or `/tmp/canopy-XX` for testing inside a worktree, never bare `canopy`, and to run `canopy use <workspace>` when the user asks to switch active canopy.

### Commit 4: `canopy upgrade` + `install.sh` + README + CHANGELOG
- `cmd/canopy/upgrade.go` (new): refuse on DEV binaries; curl `https://raw.githubusercontent.com/oncactus/canopy/main/VERSION`; string-compare to running version; if newer, print CHANGELOG.md diff (sections newer than current), then `git -C ~/.canopy/src pull --ff-only && make -C ~/.canopy/src install`. Refuse cleanly if `~/.canopy/src` missing or not a git repo (point at install.sh).
- `cmd/canopy/upgrade_test.go` (new): up-to-date no-op, network failure, missing source dir, dev-binary refusal. Mock `curl` via injectable `httpFetcher` interface.
- `install.sh` (new): bash script, ~80 lines. Detect OS via `uname -s`/`uname -m`. Check git/tmux/Go presence and versions; if missing, print exact OS-specific install command and exit 1. `git clone https://github.com/oncactus/canopy.git ~/.canopy/src`. `cd ~/.canopy/src && make install`. Print PATH hint if `~/.local/bin` is not on PATH. Idempotent: if `~/.canopy/src` exists, suggest `canopy upgrade` instead.
- `README.md`: rewrite with sections — **Prerequisites**, **Install** (curl one-liner), **Update** (`canopy upgrade`), **Uninstall** (`make uninstall` from `~/.canopy/src` + cleanup hints), **Dev workflow** (`canopy use`, `make dev`, `make release`).
- `CHANGELOG.md`: new entry for this release describing install.sh + canopy use + canopy upgrade + tmux fix.
- `VERSION` bump.

## Failure modes

For each new codepath, one realistic production failure scenario and the response:

| Codepath | Failure | Response |
|---|---|---|
| `install.sh` curl|sh | Network drops mid-clone | `set -e` aborts, no partial state, retry message |
| `install.sh` curl|sh | `~/.local/bin` not writable | check before write, suggest changing PREFIX |
| `install.sh` curl|sh | Unknown OS/arch | refuse early with "supported: linux, darwin × amd64, arm64" |
| `install.sh` curl|sh | Go too old (<1.22) | refuse with exact upgrade command per OS |
| `install.sh` curl|sh | tmux too old (<3.2) | refuse with upgrade command (popup needs 3.2+) |
| `install.sh` curl|sh | `~/.canopy/src` already exists | print "looks like canopy is already installed, run `canopy upgrade`" and exit 0 |
| `canopy upgrade` | GH raw VERSION 404/network | bail with "could not check for updates: <reason>", non-zero exit |
| `canopy upgrade` | git pull merge conflict | bail before `make install`, point at `~/.canopy/src` for manual resolution |
| `canopy upgrade` | `make install` fails | bail with last 20 lines of output, leave src dir in pulled-but-not-installed state |
| `canopy upgrade` | DEV binary | refuse with "you're on a dev build; switch with `canopy use release` first" |
| `canopy upgrade` | `~/.canopy/src` not a git repo | refuse with "src dir corrupt; delete `~/.canopy/src` and re-run install.sh" |
| `canopy use release` | `canopy.bin` missing | refuse with "no release installed; run `make install` on main first" |
| `canopy use <ws>` | `./canopy` missing | suggest `canopy use --build <ws>` or `make build` in that worktree |
| `canopy use <ws>` | unknown workspace name | refuse with `canopy use` listing of known names |
| `canopy use` | symlink target outside `~/.local` | refuse to flip, suggest manual investigation |
| Tmux popup with bare `canopy` | `canopy` not on PATH | tmux popup shows shell error inline (acceptable, visible) |
| TUI DEV detection | binary path not in a git worktree | fall back to `DEV (untracked)` instead of crashing |

**Critical gap covered:** `canopy upgrade` on shared NAT could hit raw.githubusercontent rate limits. Mitigation: cache the VERSION lookup result for 1 hour in `~/.canopy/.upgrade-check`, refresh on cache miss. Fail open if rate-limited (assume up-to-date, non-fatal).

## NOT in scope

- **Goreleaser + binary releases.** Layer C → A migration if non-Go users show up. Not needed now.
- **Homebrew tap, AUR, apt/yum/pacman, Snap, Flatpak.** No demand. Source-based covers the audience.
- **Windows.** Canopy needs tmux. Out of scope structurally.
- **macOS code signing/notarization.** Non-issue with source builds — user compiles locally, no Gatekeeper.
- **Background update checks.** Explicit `canopy upgrade` only. No daemon, no idle network calls. User retains control.
- **`canopy use --watch` (auto-flip on worktree changes).** Premature.
- **Per-workspace tmux popup binaries.** Single global symlink is intentional; lets the user spin one feature at a time deliberately.
- **`canopy use` history/undo.** YAGNI.
- **Auto-rebuild on commit (post-commit hook, `make watch`).** Separate concern, can ship as its own ~5-line `make watch` target later if desired.
- **Auto-tagging.** Tags stay manual and optional.

Lanes 1 (tmux fix) and 2 (Makefile + visuals) are independent and could parallelize. Lane 3 depends on Lane 2's Makefile changes. Lane 4 depends on Lane 3 for the `canopy use release` hint message. **In practice we ship serially as four commits in one PR** since the diff is small and the dogfood payoff comes from all-or-nothing landing.

## Acceptance

- `curl -fsSL https://raw.githubusercontent.com/oncactus/canopy/main/install.sh | sh` on a fresh Linux/macOS box → working `canopy` on PATH, `canopy version` prints clean release info
- `canopy upgrade` from yesterday's clone → today's HEAD with no manual git steps, CHANGELOG diff shown before pull
- `canopy use feature-A`, `canopy use feature-B`, `canopy use release` — each flips without rebuild, each under 100ms
- TUI status bar reflects active state across all switches; tmux statusline shows `[DEV:branch]` only when running canopy is dev
- `canopy install tmux` not re-run after binary swaps; popup keybind always invokes the active canopy
- Claude in workspace A running tests uses `./canopy` per CLAUDE.md guidance, never bare `canopy`, even when global symlink points at workspace B
- `canopy version` from any binary surfaces enough info to debug "which canopy is this" in seconds
