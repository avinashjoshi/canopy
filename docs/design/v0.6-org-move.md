# v0.6 — repo migration to `oncactus/canopy`

Plan for moving canopy out of `avinashjoshi/canopy` into the `oncactus` GitHub organization. Pairs with the public-release readiness work; this is the move that turns canopy from "Avi's personal repo" into "shippable open source under a brand."

This is a planning doc, not a checklist of things already done. Land the prerequisites first (parallel agent's work merged, decisions on this page made), *then* execute the sequence at the bottom.

## Why now

- `ancient-hornet` shipped (commits `8a3d143`…`c7903fb`): global TUI, init splash, schema v1→v2 migration, basename uniqueness gate. The architecture is stable enough to put a brand on.
- The README already has Linux/macOS/Windows install instructions and a "License TBD before public release" line — both signals canopy is heading public.
- Every additional commit at `avinashjoshi/canopy` is one more commit anyone has to mentally re-home when the move happens. Move sooner = cheaper.
- 37signals/Basecamp pattern: dev tooling lives under the *flagship product brand* (`basecamp/kamal`), not the corporate entity (`37signals/*`). Same reasoning routes canopy to `oncactus` (cactus brand) rather than `cravd` (legal entity).

## Goals

1. Canonical home is `github.com/oncactus/canopy`. Module path is `github.com/oncactus/canopy`.
2. Old URL `github.com/avinashjoshi/canopy` redirects (GitHub transfer handles this automatically).
3. License committed (Apache-2.0 recommended — see decisions below).
4. README, docs, and code comments reference the new path consistently. No straggling `avinashjoshi` mentions.
5. `go install github.com/oncactus/canopy/cmd/canopy@latest` works for a fresh user with nothing pre-installed.
6. Existing dogfood install on Avi's machine continues to work after a single `go install` re-run at the new path.

## Non-goals

- **Not** rewriting git history. The 60+ commits before the move stay attributed to `Avi Joshi <avinash@oncactus.com>` (and Claude co-authors) at their original timestamps.
- **Not** registering a vanity import path (`canopy.oncactus.dev`). Adds DNS + redirect-server complexity for a project at this scale; revisit if we ever move orgs again.
- **Not** publishing to Homebrew/AUR/`apt`/etc. yet. That's downstream of the v0.1.0 tag, not part of this move.
- **Not** doing anything with the in-flight parallel work. Whatever the other agent ships keeps shipping at `avinashjoshi/canopy` until they merge; org move waits.

#### Decision background (kept for context)

Recommendation was: **Apache-2.0**.

| | Apache-2.0 | MIT | GPL-3.0 |
|---|---|---|---|
| Permissiveness | Permissive | Most permissive | Copyleft (viral) |
| Patent grant | Explicit | Implicit only | Explicit |
| Conductor-refugee comfort | Familiar (k8s, Docker, Go ecosystem) | Familiar (Node ecosystem) | Less common in dev-tooling space |
| File overhead | LICENSE + small per-file header optional | LICENSE only | LICENSE + per-file header recommended |

Why Apache-2.0: standard for Go dev tooling (Kubernetes, Docker, Hugo, Cobra itself), explicit patent grant matters more than you'd think when a corp adopts your tool, and "if in doubt, do what Cobra/Bubbletea do" — both are Apache-2.0.

Why MIT instead: shorter file, same permissiveness for non-patent purposes, what helmor.ai uses (probably). Defensible if you want maximum brevity.

Avoid GPL: forces downstream projects to also be GPL, kills corporate adoption story for a dev-tooling project.

### D2 — Repo move method — DECIDED: **GitHub Transfer** (Avi 2026-04-28)

Recommendation: **GitHub Transfer** (`Settings → Transfer ownership`).

Why: preserves stars, watchers, issue/PR history, and — critically — auto-redirects every old URL (clones, links in tweets, archived blog posts) to the new location *forever*. The recreate-fresh path loses all of that for zero gain.

Caveat: transfer requires you to be an owner of the target org. Make sure `oncactus` org exists and you're an owner before clicking the button. (Confirm with: `gh api orgs/oncactus -q .login` returns "oncactus".)

### D3 — Module path strategy — DECIDED: **hard cut** (Avi 2026-04-28)

Recommendation: **hard cut to `github.com/oncactus/canopy`**. No vanity path, no compatibility shim.

Reasoning: real downstream count is 1 (Avi's laptop). A `go install` at the new path is two seconds. Vanity import paths (`canopy.oncactus.dev`) are reasonable insurance against *future* org moves but add a DNS record + a tiny redirect server to maintain *now*. Skip until there's a reason.

If we ever need a redirect later, Go's vanity-import pattern is a single HTTP endpoint serving a `<meta name="go-import">` tag — well-documented, easy to retrofit.

### D4 — `v0.1.0` tag timing — DECIDED: defer to my recommendation (Avi 2026-04-28)

Recommendation: **two separate commits, two separate tags-or-not.**

1. The org-move commit lands as a normal commit on `main`. No tag.
2. v0.1.0 tag goes on a *later* commit — once the post-move smoke test (clean checkout + `make install` + create + remove a workspace) passes and the README/license are confirmed clean.

Why: tagging a release at the same commit as the rename hides the "did the rename break anything?" verification window. Separating them lets us sit on the move for a day or two without the social pressure of a Show-HN-tomorrow tag attached to it.

### D5 — Coordination with parallel agent — DECIDED: **wait for merge** (Avi 2026-04-28)

The parallel agent is currently working on a feature branch off main. Org move can't start until that work has merged into main, otherwise the parallel branch's `imports` refer to `avinashjoshi/canopy` which won't exist post-rename.

Action: before kicking off the migration, confirm the parallel agent's branch is merged. If it's still in flight, let them finish. The move is a linear sequence; no benefit to interleaving it with other work.

## Sequencing

**Pre-move (do these first, in any order):**

1. Decide D1–D4 above.
2. Wait for parallel agent's branch to merge into `main`.
3. Confirm `oncactus` org exists on GitHub and Avi has owner privileges.
4. Push everything currently on `main` to `avinashjoshi/canopy`. Working tree must be clean.
4a. **Preserve Claude + gstack state** (verified 2026-04-28; zero risk for Claude, low risk for gstack with a cheap safeguard):
   - **Claude memory** lives at `~/.claude/projects/-home-avi-Work-canopy/` and is keyed by *absolute filesystem path*. The org move changes the git remote URL, NOT the local clone path. As long as you don't move `~/Work/canopy/` somewhere else, every memory file (this conversation, `MEMORY.md`, the canopy_*.md entries) stays put. Same for every per-workspace claude conversation under `~/.claude/projects/-home-avi--canopy-workspaces-canopy-*/`.
   - **gstack project data** at `~/.gstack/projects/canopy/` is found via a slug cached at `~/.gstack/slug-cache/_home_avi_Work_canopy` (value: `canopy`). The cache is path-keyed and gets hit before any git-remote logic runs, so the slug stays `canopy` post-move. But if someone clears the cache (or gstack-slug is upgraded to skip the cache), recompute from the new remote would yield `oncactus-canopy` and orphan the existing dir. Cheap insurance: copy the dir so either slug works.
     ```bash
     # Run BEFORE GitHub transfer (step 5). Idempotent: re-running is safe.
     cp -an ~/.gstack/projects/canopy/. ~/.gstack/projects/oncactus-canopy/ 2>/dev/null
     ```
     `cp -an` won't clobber existing files if `oncactus-canopy/` already has content.
   - **Per-canopy-workspace state** (`~/.canopy/workspaces/canopy/<name>/`, `~/.canopy/state.json`): unaffected. Workspace dirs are keyed by project basename which stays `canopy`. State.json's v2 schema keys by canonical absolute project root (`/home/avi/Work/canopy`) which doesn't change.

**The move itself (single sitting, ~30 min, one PR):**

5. GitHub: Settings → Transfer ownership → target `oncactus`. Wait for transfer email confirmation.
6. Locally: `git remote set-url origin git@github.com:oncactus/canopy.git`. (Or https equivalent.)
7. `git fetch && git pull` — confirm new remote works.
8. Find/replace `github.com/avinashjoshi/canopy` → `github.com/oncactus/canopy` across the repo. Affected files (39 confirmed by survey):
   - `go.mod` (1 line)
   - All `*.go` files under `cmd/` and `internal/` (every import line)
   - `README.md`, `CLAUDE.md`, `TODOS.md`
   - Every file under `docs/`
   - `Makefile` (if it references the URL)
9. `go test ./...` and `go test -tags=e2e ./...` — both green.
10. `make install && canopy version && canopy ls` (with `CANOPY_ALLOW_NESTED=1` for the ls if running inside tmux) — sanity check.
11. Commit: "Migrate to oncactus org (`avinashjoshi/canopy` → `oncactus/canopy`)".
12. Push to `oncactus/canopy` main.

**Post-move (separate commits, in order):**

13. Add `LICENSE` file (Apache-2.0 text, copyright "Cravd Inc" or "Avinash Joshi" — Avi's call).
14. README: add a one-line license note where the "License TBD" line is now. Add badges (Go Reference, Go Report Card if desired) at the top.
15. Smoke test on a fresh clone: `git clone git@github.com:oncactus/canopy.git /tmp/canopy-fresh && cd /tmp/canopy-fresh && make install` — make sure it works clean.
16. Tag `v0.1.0`. `git tag -a v0.1.0 -m "v0.1.0" && git push --tags`.
17. Update Avi's local memory entries (`canopy_org_move.md` → mark done; `canopy_local_bin.md` if it references paths).
18. Optional: tweet / Show-HN / blog post.

## Mechanical migration recipe

For step 8, the find/replace can be a single command:

```bash
# Run from repo root. Skips .git, vendor, and binary files.
git ls-files | xargs sed -i 's|github.com/avinashjoshi/canopy|github.com/oncactus/canopy|g'
```

Verification:

```bash
grep -rln 'avinashjoshi/canopy' . | grep -v '^./.git/'
# Expected: empty output
```

Note: `Co-Authored-By` lines in commit *messages* won't change (sed only edits the working tree, not git history). That's intentional — historical record stays historical.

## Risks and mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| Parallel agent's branch references old import path; merge after rename breaks | High | Wait for parallel work to merge BEFORE starting move. Stated as D5. |

| GitHub transfer fails because `oncactus` org doesn't exist or Avi lacks owner perms | Medium | Pre-flight check: `gh api orgs/oncactus -q .login` returns "oncactus" AND `gh api orgs/oncactus/memberships/avinashjoshi -q .role` returns "admin". Step 3 in pre-move sequence. |
| README install commands that users have copy-pasted into shell history still point at old path | Low | GitHub auto-redirect handles HTTPS clones. `go install` at the old path serves the last-cached version. Fine. |
| Goreleaser / future release tooling assumes old module path | Low | No goreleaser config exists today (survey: no `.goreleaser*` files, no `.github/` workflows). When release tooling lands, it'll be authored against the new path. |
| Stale `~/.canopy/state.json` references absolute paths under `~/Work/canopy` that change if Avi moves the local clone | Low | He's not moving the local clone. State is path-keyed in v2; same path stays valid. |
| Claude memory (`~/.claude/projects/-home-avi-Work-canopy/`) orphans if local clone is renamed | Zero (verified) | Path-keyed by absolute clone path. Org move doesn't touch the clone path. Don't rename `~/Work/canopy/`. |
| gstack project data (`~/.gstack/projects/canopy/`) becomes unreachable when slug recomputes from new remote | Low (verified) | Slug is cached at `~/.gstack/slug-cache/_home_avi_Work_canopy` (value: `canopy`).
