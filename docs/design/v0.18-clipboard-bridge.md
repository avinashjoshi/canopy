# Design: Clipboard bridge for remote hosts (v0.18)

Repo: github.com/avinashjoshi/canopy

(`internal/ui/update_clipboard_autosetup.go`). Auto-installs on first connect —
Lane B's per-laptop bootstrap and Lane C's per-host install both run
unattended, keyed off a sanitized artifact name

(`user@host:port`) never needs `canopy host add` first. The manual `c`
keybind and `canopy host clipboard <name>` CLI path (Premise 1's per-host
opt-in) are unchanged for ordinary multi-host usage; `canopy host clipboard`
now also accepts a raw target via the same `resolveRemoteHost` fallback
`--remote`/`--on` use, rather than requiring registry lookup.

**v0.24.x follow-up — replaced the mechanism, not just wired more of it
in:** everything below this note (the daemon, the persistent SSH tunnel,
`RemoteForward`, the per-host `~/.ssh/config.d/canopy/<name>.conf`
snippet, `socat`, UID detection) describes the *original* v0.18
architecture and is kept for historical context, not as current
behavior. Dogfooding surfaced a laptop-side systemd unit stuck in
`StartLimitBurst` ("start of the service was attempted too often") that
took manual `systemctl --user reset-failed` to clear — which, combined
with a look at how [herdr](https://herdr.dev) solves the same problem,
prompted retiring the whole daemon/tunnel design for **text** clipboard
in favor of OSC 52 terminal escape sequences: `wl-copy`/`wl-paste` now
talk directly to the attached terminal (`\033]52;c;...\033\\`, wrapped
in tmux's DCS passthrough envelope when inside tmux), which needs no
laptop process, no forwarded sockets, and no `socat` on the remote.
Image support is dropped in this rewrite — OSC 52 payloads are too
size-constrained for screenshots — and is tracked as a separate future
PTY-proxy effort, not part of this change. `canopy host clipboard
<name>` now also actively tears down any pre-OSC52 artifacts (the
tunnel unit, the daemon unit, the SSH snippet) it finds on the laptop,
which directly resolves the `StartLimitBurst` case instead of requiring
manual intervention.

User-facing reference + troubleshooting (current, OSC52-based mechanism):
[`docs/clipboard-bridge.md`](../clipboard-bridge.md).

## Problem statement

v0.17.x moved canopy workspaces off the laptop and onto remote Linux hosts. The dispatch loop works; mosh-attach works; agents run in the background while the laptop sleeps. One thing got worse along the way: clipboard.

On the laptop, a developer pasting an image into Claude Code inside tmux Just Works. Claude reads the local clipboard via `wl-paste --type image/png` and ingests the bytes. The same flow inside a remote canopy workspace fails silently — the remote `wl-paste` reads the *remote* host's clipboard, which is empty (or, on a headless server, doesn't exist at all). Same for text: copying a snippet out of the remote agent's output into the laptop's clipboard requires the user to manually highlight-and-OSC52, with terminal-specific quirks for tmux passthrough.

The result is a step-function downgrade in the perceived quality of remote workspaces. The laptop case is invisible (it just works); the remote case forces the user to think about clipboard plumbing every time they paste a screenshot to an agent. For a "fleet of agents" thesis where pasting context to an agent is core, this is a daily-driver tax.

The narrow goal: make `wl-paste` / `wl-copy` on every registered canopy host behave as if it were reading the laptop's clipboard. Per-host opt-in, surfaced in the Hosts tab, set up with one keypress.

## What makes this cool

You wake up. You run `canopy` on your laptop. The Hosts tab shows `tower ● online  v0.18  📋 bridged`. You attach into a workspace on tower, ask Claude Code something, screenshot a chart from your local browser, Ctrl+V into Claude's prompt — the image lands. You didn't think about it. Claude on tower received the same bytes Claude on the laptop would have received.

The "whoa" demo is exactly two keystrokes: cursor onto a host row, press `c`. Canopy probes the local clipboard tool, installs a systemd user service on the laptop, writes an `~/.ssh/config.d/canopy/<host>.conf` snippet, SSHes to the remote, drops in two wrapper scripts, verifies end-to-end, and flips the status pill. Total time: under five seconds on a warm SSH connection.

Tagline: **the laptop's clipboard, available to every remote canopy host, with no per-session setup.**

The deeper thing this unlocks: clipboard becomes invisible plumbing again, the way it was in v0.16. v0.17 made remote workspaces feel real; v0.18 makes them feel native.

## Constraints

- **No daemon on the wire.** Use SSH `RemoteForward` of Unix sockets. Same transport canopy already uses for everything else (SSH+ControlMaster); no new ports, no new network exposure, no third-party clipboard-share service.
- **Wayland local + Linux remote only in Phase 1.** X11 (`xclip`) and macOS (`pbpaste`/`pbcopy`) providers defer to Phase 2 — locked at /plan-eng-review. v0.18 audience is one user on Hyprland/Wayland; cross-platform breadth before a second user exists is a token poorly spent. Adding a provider later is a single-file change because the `Provider` interface is in place from Phase 1.
- **One binary, not two.** The clipboard daemon ships as a `canopy clipboard-server` subcommand of the existing canopy binary. No second goreleaser target, no second update path.
- **No mutation of `~/.ssh/config`.** Use `Include ~/.ssh/config.d/canopy/*.conf` for canopy-managed snippets; never touch the user's main file. The Include directive itself is added once via a marker-block edit mirroring `cmd/canopy/install_tmux.go`'s `# canopy:start` / `# canopy:end` pattern.
- **Idempotent.** Re-press `c` on an already-bridged host is safe. Re-installs the systemd unit, overwrites the wrappers with the current bundled version, refreshes the SSH snippet.
- **No image-paste fallback that re-implements clipboard.** Claude Code already knows how to read the clipboard via `wl-paste`. The bridge intercepts at the same syscall the existing code path uses — no protocol invention.
- **First-time Go discipline.** Stay stdlib-shaped. Embed scripts via `embed.FS`, push them over the existing `SSHCmd` plumbing, no new long-running goroutines beyond the three socket listeners in the daemon.

## Premises

1. **Per-host opt-in.** Clipboard bridge is a host-level capability, not a workspace-level one. Setup is per (laptop, host) pair; once enabled, every workspace on that host inherits it.
2. **The laptop is the clipboard authority.** Both directions flow through the laptop's clipboard tool (`wl-clipboard` on Wayland in Phase 1). The remote never has its own clipboard state — it always proxies to the laptop.
3. **Three sockets, not one.** `clip-text.sock`, `clip-image.sock`, `clip-copy.sock`. Separate the read-paths so a remote wrapper doesn't have to negotiate MIME type over a single socket. Cheap; clear.
4. **`socat` is fair game.** Every distro has it; `install.sh::detect_pkg_install` already handles apt/dnf/pacman/apk; if missing on a remote, canopy auto-installs via the host's package manager (same path v0.17.3.0 uses for canopy's own deps).
5. **No multi-laptop ownership.** Phase 1 assumes one laptop per host at a time. If two laptops both bridge to the same host concurrently, the remote sees the most recently established RemoteForward (SSH's `StreamLocalBindUnlink yes` semantics). The failure mode is "you typed on laptop A, image came from laptop B", recoverable by reconnecting from the correct laptop. Multi-laptop arbitration is a v0.19+ thesis.
6. **Probe is the source of truth for status.** The Hosts tab's `📋 bridged` pill comes from the remote canopy itself reporting its bridge state inside `canopy ls --json` — same channel as `canopy_version`. The user can break the bridge by hand (delete a wrapper, kill the daemon) and canopy will notice within one refresh tick.
7. **Daemon binary path follows the user's `canopy use` symlink.** The systemd unit's `ExecStart=%h/.local/bin/canopy clipboard-server` points at whichever canopy is currently active, so `canopy use release` / `canopy use <workspace>` swaps don't break the daemon. Matches the multi-workspace dogfooding contract in CLAUDE.md.

## Architecture

```
laptop                                            remote host (tower / fly-iad / etc)
─────────────────────────────────────────       ─────────────────────────────────────
~/.local/bin/canopy (active symlink)            ~/.local/bin/wl-paste  (canopy wrapper)
  ↑ canopy use <workspace> | canopy use         ~/.local/bin/wl-copy   (canopy wrapper)
    release flips this                          ~/.local/bin/canopy    (reports
~/.config/systemd/user/                                                  ClipboardBridge
  canopy-clipboard.service                                               in `canopy ls --json`)
  → ExecStart=%h/.local/bin/canopy clipboard-server
~/.ssh/config (marker-block Include)
  → Include ~/.ssh/config.d/canopy/*.conf
~/.ssh/config.d/canopy/<host>.conf
                                          ▲
                                          │ SSH RemoteForward (3 unix sockets)
                                          │   clip-text.sock   text  ────►  remote read
                                          │   clip-image.sock  image ────►  remote read
                                          │   clip-copy.sock   text  ◄────  remote write
                                          │
local clipboard ◄──── reads ─── daemon ◄──┘ ◄──────────────── Claude Code on remote
(wl-paste, wl-copy)              │                              (calls wl-paste, hits
                                 └── three socket listeners       canopy wrapper, which
                                                                  proxies to the laptop)
```

### Daemon (`canopy clipboard-server` subcommand)

Subcommand of the canopy binary; not a separate goreleaser target. Launched by systemd user unit at `~/.config/systemd/user/canopy-clipboard.service` with `ExecStart=%h/.local/bin/canopy clipboard-server`. The symlink path lets `canopy use <workspace>` and `canopy use release` swap the active binary without breaking the daemon (Premise 7).

Listens on three sockets in `$XDG_RUNTIME_DIR/canopy/`:

- `clip-text.sock`  — every connection, server calls `Provider.ReadText()`, writes bytes, closes.
- `clip-image.sock` — every connection, server calls `Provider.ReadImage("image/png")`, writes bytes, closes.
- `clip-copy.sock`  — every connection, server reads stdin until EOF, calls `Provider.Write(bytes)`, closes.

`Provider` interface (single Wayland impl in Phase 1) abstracts the actual clipboard tool. Systemd unit's `Restart=on-failure` recovers from a wedged provider call without user intervention.

### SSH config snippets

`~/.ssh/config.d/canopy/<host>.conf`:

```
Host <host>
  RemoteForward /run/user/<REMOTE_UID>/canopy/clip-text.sock  /run/user/<LOCAL_UID>/canopy/clip-text.sock
  RemoteForward /run/user/<REMOTE_UID>/canopy/clip-image.sock /run/user/<LOCAL_UID>/canopy/clip-image.sock
  RemoteForward /run/user/<REMOTE_UID>/canopy/clip-copy.sock  /run/user/<LOCAL_UID>/canopy/clip-copy.sock
  StreamLocalBindUnlink yes
```

UIDs detected at install time: laptop UID from `os.Getuid()`, remote UID from `ssh <target> id -u`. Baked into the snippet. Re-detection happens on `canopy host clipboard <name> --reinstall` (the `c` key's Repair affordance triggers this).

`~/.ssh/config` is touched exactly once across the laptop's lifetime — to add the `Include ~/.ssh/config.d/canopy/*.conf` directive — between marker comments mirroring `cmd/canopy/install_tmux.go:33-46`:

```
# canopy:start clipboard-bridge ...
Include ~/.ssh/config.d/canopy/*.conf
# canopy:end clipboard-bridge
```

Subsequent host installs only write the per-host snippet file; the user's main `~/.ssh/config` stays untouched after the one-time bootstrap.

### Remote wrappers

Two shell scripts, both embedded via `embed.FS` and pushed via stdin to `cat > ~/.local/bin/<name>` (same pattern as `internal/host.InstallScript`):

- `wl-paste` — parses `--type`, `--list-types`, `--no-newline`, routes to the appropriate forwarded socket. Probes `clip-image.sock` lazily for `--list-types` so the laptop knows when an image is on offer.
- `wl-copy` — reads stdin, writes to `clip-copy.sock`. Ignores most wl-copy flags (`--paste-once`, `--primary`, etc.); for canopy's use case "the local clipboard" is one bucket.

Every `socat` invocation in a wrapper is wrapped with `timeout 2`, so a daemon-down or broken-forward state fails fast within 2 seconds rather than hanging Claude Code's Ctrl+V indefinitely.

Wrappers carry a version comment header (`# canopy clipboard-bridge — managed by canopy v<canopy-version>; hash:<content-sha256-12>`); reinstall fast-skips when the on-remote hash already matches the bundled wrapper's hash.

### Probe transport — folded into `canopy ls --json`

The remote canopy reports its clipboard-bridge status inside its existing `canopy ls --json` JSON envelope, alongside `canopy_version`. The laptop's `internal/host/refresh.go::refreshOneHost` parses one extra field. **No second SSH round-trip per refresh tick.**

Remote-side probe (in `cmd/canopy/ls.go`): once per `canopy ls --json` invocation (each is a fresh canopy process per the v0.17 "CLI per request, no daemon" model), check:

1. Wrappers present at `~/.local/bin/wl-paste` AND `~/.local/bin/wl-copy`? If no → `off`.
2. `wl-paste --list-types` returns within 2s with `text/plain` in output? If yes → `bridged`. If no → `broken`.

Three reportable states emitted to the laptop:

- `bridged` — wrappers present, probe succeeds.
- `broken` — wrappers present, probe fails (daemon down, sshd `AllowStreamLocalForwarding no`, socket forward broken, etc.).
- `off` — wrappers absent.

Result lands in `state.RemoteHostSnapshot.ClipboardBridge` (string enum).

## Approaches considered

### Approach A: SSH RemoteForward of Unix sockets (CHOSEN)

The architecture above. Zero new transports, zero new daemons exposed to the network. The laptop's clipboard tool and the remote's CLI surface are linked by SSH-mediated socket plumbing that canopy sets up once and forgets about.

Trade-offs: requires `socat` on both ends (auto-install path exists). Requires the remote sshd to allow stream-local forwarding (default-yes on every distro we care about; if disabled, canopy detects and tells the user the one-line sshd_config fix). Per-laptop ownership of a host at any one time (Premise 5).

### Approach B: Dedicated clipboard daemon with custom TCP protocol

Run a small RPC server locally (gRPC/HTTP), bind it to a localhost port, forward the port to the remote via SSH `LocalForward`. Remote wrappers POST/GET text and image bytes.

Rejected: more moving parts, more attack surface, a custom protocol to test and version. The Unix-socket approach uses primitives every Linux box already has, and SSH's built-in forwarding is the most battle-tested transport on the planet.

### Approach C: OSC 52 only (text), no image bridge

Configure tmux/terminal for OSC 52 passthrough; punt on image clipboard entirely.

Rejected: text-only is the v0.17 status quo and it's exactly the experience this design fixes. Image paste is the load-bearing case — pasting screenshots into Claude is the default agent workflow.

### Approach D: lemonade or universal-clipboard

Adopt an existing cross-platform clipboard-share tool.

Rejected: those tools target a different use case (text-first, persistent daemon on both ends, optional encryption). Image support is patchy. Adding a third-party daemon to every canopy host changes the deployment story for a feature that's better served by 50 lines of shell-and-socat over plumbing canopy already has.

## v0.18 scope

### Phase 0 — Validation (afternoon hack)

Smallest version that proves the loop end-to-end against a single hardcoded host:

- `internal/clipboard/Provider` interface + Wayland (`wl-clipboard`) implementation.
- `canopy clipboard-server` subcommand listening on three sockets, started manually (`canopy clipboard-server &`).
- Hand-written SSH config snippet for one host.
- Hand-written `wl-paste` / `wl-copy` wrappers on one host.
- Manual verification: `ssh tower -- wl-paste --list-types` lists `image/png` when laptop clipboard has a PNG; image bytes flow.
- No TUI integration, no probe, no auto-install.

If image flow doesn't feel native after 20 minutes of dogfooding, stop and rethink. If it does, ship Phase 1.

### Phase 1 — Production shape

- `internal/clipboard/` package: `Provider` interface + Wayland impl + `embed.FS` wrappers + snippet generator + install/probe orchestration.
- `canopy clipboard-server` subcommand of the existing binary (no separate release target).
- Local-side bootstrap: `canopy install clipboard-bridge` subcommand (peer of `canopy install tmux`). Writes the systemd user service, enables it, and adds the `~/.ssh/config` marker-block Include directive if absent. One-time per laptop.
- Per-host setup: `canopy host clipboard <name> [--reinstall|--uninstall]` CLI verb. Detects remote UID, writes per-host SSH snippet, pushes wrappers, auto-installs `socat` on the remote if missing.
- TUI integration on the Hosts tab:
  - New `c` keybinding: opens a confirmation modal ("Install clipboard bridge on `<host>`?") that runs `canopy host clipboard <name>` with output streaming into the existing install drawer (reuses `update_host_upgrade.go` machinery).
  - New status pill rendered after the canopy-version pill at ≥80c: `📋 bridged` (green), `📋!` (amber for broken), nothing for off.
  - Detail view (`enter` on a host row) gains a "Clipboard bridge" section with status, last refresh time, snippet path, and a "Repair" affordance that triggers `canopy host clipboard <name> --reinstall`.
- Probe folded into `cmd/canopy/ls.go`'s JSON output. New `state.RemoteHostSnapshot.ClipboardBridge` field. Refresher's `parsed.ClipboardBridge` lands on the snapshot — no separate probe path.

### Phase 2+ (deferred, captured in NOT-in-scope below)

- X11 (`xclip`) local provider. Single-file addition to `internal/clipboard/`.
- macOS local (`pbpaste`/`pbcopy`) provider. Single-file addition.
- macOS remote support (`pbpaste`/`pbcopy` wrappers).
- Multi-laptop arbitration / claim tokens.
- Encrypted/audit-logged mode (compliance feature; needs separate security review).
- Selection-clipboard (X11 PRIMARY) support.

### Dogfood-discovered failures (and the fixes that shipped in v0.18)

These are the bugs that took a 90-minute dogfood session to surface,
each with a permanent fix in the v0.18.0 release.

| # | Symptom | Root cause | Fix |
|---|---------|------------|-----|
| 1 | `ls --json` probe ran but reported nothing useful; SSH `-v` showed `remote software version Tailscale` | Tailscale SSH intercepting; doesn't support Unix-socket forwarding | Documented as a setup prerequisite. User must `tailscale set --ssh=false` on the bridged host. Future: detect in verify and emit specific error |
| 2 | `ssh -G <target> \| grep remoteforward` returned empty even though the snippet file was correct | Snippet used `Host {{.HostName}}` (canopy alias). SSH matches `Host` against the *hostname portion* of the target string. `ssh user@hostname` never matched `Host tower` | Snippet now uses `Host canopy-tunnel-<name>` — a dedicated alias only the persistent tunnel uses. Normal `ssh user@host` doesn't match it, so it doesn't conflict |
| 3 | After (2) fixed: `ssh -G` STILL showed no RemoteForward despite the snippet being correct | Snippet's `Include` directive was appended at the bottom of `~/.ssh/config`, which placed it inside the last preceding `Host <other>` block. Comments don't terminate Host blocks; only another `Host` or `Match` does. The Include was conditional on matching the wrong host | Marker block now wraps the Include in `Host *` so it's unconditional. EnsureSSHInclude also rewrites stale marker blocks (the v0.18 install rewrites the broken shape from earlier dogfood) |
| 4 | After (3) fixed: SSH established the forwards (warnings stopped) but `wl-paste` on remote said "No such file or directory" for the socket path | Parent dir `/run/user/<uid>/canopy/` didn't exist on the remote. sshd doesn't `mkdir` parent dirs before `bind()`; `bind()` returns ENOENT and silently warns "remote port forwarding failed" | Install now `mkdir -p /run/user/<uid>/canopy && chmod 0700` on the remote between UID detection and wrapper push |
| 5 | The mkdir step itself failed with `mkdir: missing operand` | `bash -c "mkdir -p X && chmod Y X"` over SSH: SSH joins post-target args with spaces, remote shell re-tokenizes, `bash -c` receives only `mkdir` as its script and the rest become positional args of the sub-bash (silently dropped) | Switched all multi-token bash invocations to pipe scripts via SSH stdin to a bare `bash`. Done in three commits across mkdir, verify-wrapper, verify-path |
| 6 | Verify still failed with "Connection refused" or stale-socket errors on re-install | `StreamLocalBindUnlink yes` in the snippet isn't reliably honored by sshd. Sockets from a prior crashed/expired session remained on the remote and blocked bind() | Tunnel unit's `ExecStartPre` SSHes to the remote and `rm -f` the three socket paths before the main `ssh -N` attempts to bind |
| 7 | Bridge was working but only briefly (~5 min after install); then `wl-paste` started failing again | canopy's own SSH `ControlMaster` (with `ControlPersist=300`) was the only thing holding the forwards alive. After 5 min idle, master exited, sshd cleaned up the sockets, bridge died | Persistent systemd user unit per host runs `ssh -N canopy-tunnel-<name>` continuously, supervised by `Restart=on-failure`. Independent of canopy's TUI being open or any user-initiated SSH |
| 8 | tmux copy-mode selections didn't reach the local clipboard despite the bridge being functional | tmux didn't know to pipe its selection through wl-copy. The bridge mechanism is correct; the UX integration was missing | Install splices `bind-key -T copy-mode-vi y/Enter/C-S-c/MouseDragEnd copy-pipe-and-cancel "wl-copy"` into the remote's `~/.tmux.conf` via marker block. `tmux source-file` on the remote re-reads in live sessions. `set -g extended-keys on` enables modifier distinction |

### Known quirks (intentional limitations, not bugs)

| Quirk | Why | Workaround |
|-------|-----|-----------|
| Mosh-attached sessions get `Ctrl+Shift+C` translated to plain `Ctrl+C` | Mosh's wire protocol doesn't faithfully forward extended-keys (CSI-u / modifyOtherKeys) sequences | Use `y` or `Enter` in tmux copy-mode; SSH-attach when `Ctrl+Shift+C` matters |
| Terminal apps may consume `Ctrl+Shift+C` before tmux sees it | Most terminal emulators bind `Ctrl+Shift+C` to "copy terminal selection" at the app level | Rebind the terminal's copy action to a different key, OR use `y` / `Enter` / shift-bypass |
| Single laptop per host at a time | SSH `StreamLocalBindUnlink yes` means the second tunnel's bind unlinks the first's socket | v0.19+ multi-laptop arbitration with claim tokens |
| `canopy switch` mosh-attaches by default | v0.17 design decision — mosh's UDP transport is the better default for spotty connections | Delivered in v0.23.0.0 as `canopy switch --on ... --no-mosh` (ssh reconnect-loop instead of mosh; also the automatic fallback when mosh isn't installed locally) |

## Worktree parallelization strategy

Three lanes, two of them parallel-safe:

| Lane | Steps | Modules touched | Depends on |
|------|-------|------------------|------------|
| A | provider.go + wayland.go + server.go + `canopy clipboard-server` subcommand | `internal/clipboard/{provider,wayland,server}.go`, `cmd/canopy/clipboard_server.go` | — |
| B | install.go + `canopy install clipboard-bridge` subcommand | `internal/clipboard/install.go`, `cmd/canopy/install_clipboard.go` | — |
| C | host_install.go + `canopy host clipboard` + ls.go extension + state/refresh extensions + TUI | `internal/clipboard/host_install.go`, `cmd/canopy/{host_clipboard,ls}.go`, `internal/state/`, `internal/host/`, `internal/ui/` | A (server must exist for E2E), B (local-bootstrap for install affordance) |

**Execution order:** A and B in parallel worktrees. Merge both. Then C. A and B touch disjoint module subsets; conflict-free. C touches new files in `internal/clipboard/` plus existing-file extensions in `cmd/canopy/`, `internal/state/`, `internal/host/`, `internal/ui/` — safe after A+B merge because those existing files aren't edited by A or B.

## Acceptance criteria — validated 2026-05-14

**Phase 0 — daemon mechanics:** ✅ Validated. Daemon listens on three Unix sockets; socat round-trips text + image bytes correctly. systemd unit survives canopy binary swaps via the `~/.local/bin/canopy` symlink.

**Phase 1 — full end-to-end:** ✅ Validated.
- `canopy install clipboard-bridge` writes systemd unit + SSH config Include; daemon auto-starts at graphical-session activation.
- `canopy host clipboard tower` installs end-to-end including the persistent tunnel + tmux bindings; verify reports "bridge active."
- Local clipboard image → Claude Code on tower (Ctrl-V) — image attached, not pasted-as-text.
- Local clipboard text → tmux session text-paste — works.
- `wl-copy` on tower's command line → local Wayland clipboard — works via wrapper.
- tmux copy-mode `y` / `Enter` / `MouseDragEnd1Pane` → local clipboard — works via auto-installed bindings.
- tmux copy-mode `Ctrl+Shift+C` → local clipboard — works via SSH-attach (documented as not working via mosh-attach due to mosh's extended-keys limitation).

**Persistent tunnel:** ✅ Validated.
- Tunnel unit alive across daemon restart, simulated network drop, canopy TUI close.
- `systemctl --user status canopy-clipboard-tunnel-tower` shows `active (running)`.
- Bridge survives independently of any user session or canopy command activity.

**Stretch (multi-host fleet):** Not exercised end-to-end (one bridged host in dogfood); architecturally each bridge is independent (one systemd tunnel unit per host, no shared state beyond the daemon's three sockets which are read-only contended).

## Design system

Status glyph and color mapping (extends the v0.17 palette in `internal/ui/render.go`):

```
Clipboard bridge state       | lipgloss color | glyph
──────────────────────────── │ ────────────── │ ──────
bridged (probe OK)           | 46 (green)     | 📋
broken (probe fail)          | 214 (amber)    | 📋!
off (never installed)        | —              | (no pill)
```

Hosts-tab tiered width drop: clipboard pill appears at ≥80c paired with the canopy-version pill. At <80c the pill is dropped first; status remains accessible via the detail view.

A11y: glyph + suffix (`📋 bridged` / `📋! broken`), never glyph alone.
