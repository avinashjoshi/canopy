## Problem Statement

Canopy is a Go/Bubbletea TUI for managing git worktrees with paired tmux sessions and per-project setup/teardown hooks. The motivating problem is that Avi's previous workspace tooling on macOS was GUI-based and Mac-only; after switching to Arch Linux there's no equivalent. Tried Linux alternatives (Orca, Emdash) — rejected as "too busy." Tmux session managers (tmuxinator, sesh, smug) don't understand worktrees. Git-worktree CLI wrappers don't run hooks or set up tmux. Nothing on Linux fills the gap.

## What Makes This Cool

The single sentence positioning: **"TUI-first workspace manager for Linux that respects your existing terminal."**

The "whoa" demo is `canopy new` → ~10 seconds later you're attached to a tmux session with four panes (nvim on the worktree, claude CLI, free terminal, dev server running on a unique port against a fresh DB). The cognitive flow that took 10 minutes of yak-shaving is one command and a coffee sip.

What makes canopy feel right and Orca feel wrong: **calm**. One TUI list. One sharp keymap. No dashboard. No metric overlays. The features earn their pixels.

## Constraints

- **Language:** Go. **Library:** Bubbletea + lipgloss + bubbles (charmbracelet stack).
- **Author experience:** First-time Go programmer. Lean on stdlib + a small set of well-known deps. Avoid generics-heavy abstractions early.
- **OS target:** Linux (Arch / Omarchy primary). macOS support is a no-cost side effect of Go portability; Windows is not a goal.
- **Deps assumed installed:** `git` (>= 2.30 for worktrees), `tmux` (>= 3.0), the user's editor (`nvim`), the user's AI CLI (`claude`), and any per-project dev runner (e.g. `bin/dev`).
- **Must work for cravd (Rails) on day 1.** Other projects come later.

## Premises (all confirmed in session)

1. **Calm-and-focused is the soul.** Opinionated, narrow surface area, zero dashboards. The taste filter for every feature: "would this ship in a tool that prides itself on calm, or only in a kitchen-sink tool?" If the latter, it doesn't belong in canopy v0.
2. **The wedge is `canopy new <branch>`.** Ten-second worktree setup is the killer demo. Everything else supports it.
3. **TUI from day 1 (Bubbletea-first).** Subcommands exist underneath, but the TUI is the front door. *Note: this revises Avi's original "shell scripts first, TUI second" sequence — agreed during the session.*
4. **Cravd-first, multi-project later.** No abstractions for projects that don't yet exist.
5. **Hooks are the extension point, not configurable layouts.** Pane layout is fixed in v0 (nvim / claude / terminal / server). Setup and teardown commands are user-defined per-project YAML.
6. **tmux owns session persistence; canopy owns worktree-state.** Don't reinvent tmux-resurrect. Canopy's persistence is its registry of which worktrees exist.
7. **DB/env shape is a hook concern. Port allocation is a builtin** because hooks need a unique port handed in via template variable. The Rails-specific magic (DB naming, `.env.local` rewriting) lives in the user's hook recipe, not core.
8. **Distribution: AUR + `go install` from day 1.** Releases via `goreleaser` to GitHub. Skip Homebrew/apt for v0.

## Approaches Considered

### Approach A: CLI-first, TUI in v2
Ship subcommands only in v0 (`canopy new`, `canopy rm`, `canopy ls`, `canopy switch`). Add Bubbletea later as a wrapper. Fastest to v0 (one weekend), but canopy v0 is indistinguishable from `worktree-helper` until the TUI lands. Risk: stalling at v0.

### Approach B: Bubbletea-first, the TUI is the product (CHOSEN)
`canopy` with no args opens a Bubbletea TUI listing worktrees across projects. Subcommands also exist for scripting. Clean package boundaries from commit one. Two to three weekends to first dogfood. The TUI is the product, not an afterthought.

### Approach C: Daemon + thin client
`canopyd` long-running daemon serving Unix socket to a thin TUI client. Future-proof for cross-machine sync and editor integration, but classic premature architecture for one user on one box. Rejected as overbuild for v0.

## Recommended Approach: B (Bubbletea-first)

### Architecture

Single repo, single binary, package layout:

```
github.com/avinashjoshi/canopy/
├── cmd/canopy/main.go       # entry point; routes between TUI and subcommands
├── internal/
│   ├── config/               # canopy.json walk-up discovery + load
│   ├── git/                  # worktree add/remove/sanitize via os/exec wrapping git
│   ├── tmux/                 # session create/attach/kill/has via os/exec wrapping tmux
│   ├── hooks/                # script execution via exec.CommandContext + CANOPY_* env
│   ├── state/                # registry of known workspaces (JSON in ~/.canopy/state.json)
│   ├── workspace/            # ORCHESTRATION: Create/Remove/Resurrect/Reconcile
│   ├── namegen/              # random adjective-noun workspace names (e.g., bold-falcon)
│   ├── clog/                 # slog setup → ~/.canopy/log/canopy.log (named clog to avoid stdlib log collision)
│   └── ui/                   # Bubbletea Model/Update/View + lipgloss styles
├── docs/
│   ├── design/               # design docs (committed; survives ~/.gstack nukes)
│   └── reviews/              # review artifacts (test plan, etc.)
└── README.md
```

Dependency direction (no cycles):

```
                    cmd/canopy
                        │
                        ▼
          ┌──────── ui ──────────┐
          │                      │
          └──── workspace ───┐   │
                  │          │   │
        ┌─────────┼──────────┘   │
        ▼         ▼              ▼
       git      tmux           state ◄── log
                                 │        │
                                 ▼        ▼
                              config   (used by all)
```

Why these boundaries:
- `git`, `tmux`, `hooks`, `state`, `config` are leaf primitives. Each takes inputs, returns outputs/errors. Testable in isolation. No global state.
- `workspace` is the single orchestrator. Owns `Create(ctx, name)`, `Remove(name)`, `Resurrect(name)`, `Reconcile()`. Both `cmd/canopy` (subcommands) and `ui` (TUI) call into it. Mirrors lazygit's `commands/` package pattern.
- `state` is the single mutable thing. Persists to JSON (one file, simple, debuggable). Survives crashes.
- `clog` is the leaf-most package (renamed from `log` to avoid stdlib collision) — every other package imports it via a top-of-file `var log = clog.Pkg("<name>")`.
- `ui` consumes `workspace`. Bubbletea Model holds a snapshot of state; Update dispatches to `workspace` on key events; View renders via lipgloss.
- `config` is read-only at startup; no live reload in v0.

### Vocabulary

- **Workspace** — the canopy abstraction for a (git worktree + tmux session + scripts + port) bundle. Replaces "worktree" everywhere user-facing.
- **Worktree** — the git concept. Still used inside `internal/git/`. Otherwise: workspace.
- **Workspace name** — a generated `<adjective>-<noun>` (e.g., `bold-falcon`). Stable identifier for the lifetime of the workspace. Set at `canopy new` time and never auto-renamed.
- **Branch name** — the underlying git branch. Starts equal to the workspace name; can diverge if you (or AI) rename the branch later via `git branch -m`. Reconciliation tracks the rename.
- **Project** — a repo that contains a `canopy.json`. Discovered by walking up from cwd.

### Configuration

Project configuration uses a known-good schema we've already validated in production via cravd's existing tooling: a tiny JSON at the repo root, discovered by walking up from cwd:

```json
{
  "scripts": {
    "setup": "bin/canopy-setup",
    "run": "bin/dev",
    "archive": "bin/canopy-archive"
  }
}
```

That's the entire schema. Three string keys, three script paths. Each script gets the same three environment variables:

| Var                       | Meaning                                                  |
|---------------------------|----------------------------------------------------------|
| `CANOPY_WORKSPACE_PATH`   | Absolute path to the workspace dir (= git worktree dir). |
| `CANOPY_ROOT_PATH`        | Absolute path to the original repo root.                 |
| `CANOPY_PORT`             | Allocated port for this workspace (3000-3999).           |

Script semantics:
- **`setup`** — runs once when canopy creates a new workspace. Symlinks shared secrets, installs deps, creates DB, copies env files. Returns 0 on success. Failure → workspace `status: broken`.
- **`run`** — the long-running command for the server pane. Whatever you'd normally type to bring up your dev environment (`bin/dev`, `npm run dev`, `mix phx.server`). Restarted on workspace resurrection.
- **`archive`** — runs when canopy removes a workspace. Drops DB, kills server processes, cleans up. Failure logs but doesn't block removal in v0.

Scripts are executed via `exec.CommandContext(ctx, scriptPath)` (no `sh -c`) with the env vars above plus the user's existing environment, `cwd = CANOPY_WORKSPACE_PATH`. They're plain executables on PATH or in the repo.

**Migration cost from cravd's existing conductor.json:**
```bash
cd ~/Work/cravd
cp conductor.json canopy.json
sed -i 's/CONDUCTOR_/CANOPY_/g; s/conductor-/canopy-/g' canopy.json bin/conductor-*
git mv bin/conductor-setup bin/canopy-setup
git mv bin/conductor-teardown bin/canopy-archive
sed -i 's/CONDUCTOR_/CANOPY_/g' config/database.yml
```

Five minutes. The user's existing setup/teardown logic ports verbatim.

**Why JSON not YAML:** stdlib `encoding/json`, no extra dep, schema is too small to benefit from YAML's structure. The cravd tooling we're matching uses JSON; staying with JSON is one less mental translation.

**Pane layout** stays opinionated in v0 (canopy doesn't take this from config):
1. **nvim** — `nvim` in workspace dir.
2. **claude** — `claude` on first launch (`canopy new`); `claude --continue` on resurrection (`canopy switch` against a `stopped` workspace) to pick up the prior conversation. Per-directory storage under `~/.claude/projects/<dir-hash>/` means the conversation survives session death; `--continue` is the explicit "resume the most recent" flag.
3. **shell** — user's `$SHELL` in workspace dir.
4. **server** — runs `scripts.run` with the env above.

The claude command differs by entry point. canopy's pane-creation logic takes a `mode` parameter: `mode=fresh` (new workspace) → `claude`; `mode=resume` (resurrection) → `claude --continue`. Verified during pre-flight that `--continue` works across new tmux sessions in the same dir.

**v0 architecture nudge for v0.5 multi-AI:** the strings `"claude"` and `"claude --continue"` live in `internal/ai/defaults.go` as named constants (`DefaultAICmd`, `DefaultAIResumeCmd`), not inline in `internal/workspace/` or `internal/ui/`. The v0.5 layout-as-config swap then replaces the constant lookup with a config field read. ~5-line change instead of a refactor. See TODOS.md "Multi-AI-tool support" for the full v0.5 plan.

Layout-as-config is a v0.5 feature.

### State persistence

`~/.canopy/state.json` — list of known workspaces:

```json
{
  "schema_version": 1,
  "workspaces": [
    {
      "project": "cravd",
      "name": "feature-x",
      "branch": "feature-x",
      "path": "/home/avi/Work/cravd/worktrees/feature-x",
      "tmux_session": "cravd-feature-x",
      "port": 3001,
      "status": "ready",
      "created_at": "2026-04-27T16:00:00Z",
      "last_error": null
    }
  ]
}
```

In v0 `name` defaults to `branch` (canopy creates the workspace with the same identifier as the git branch). Distinct names are a v0.5 feature.

`schema_version` exists from v0 so future migrations are explicit, not lossy.

### Workspace state machine

Five statuses. Reconciliation on startup compares state.json rows to disk (`os.Stat(path)`) and to tmux (`tmux has-session -t <name>`):

```
        canopy new
            │
            ▼
      ┌──────────┐  setup fails  ┌──────────┐
      │setting_up│──────────────▶│  broken  │
      └──────────┘               └──────────┘
            │ setup ok                  │
            ▼                           │ canopy rm
      ┌──────────┐  tmux dies     ┌──────────┐
      │  ready   │───────────────▶│ stopped  │
      └──────────┘                └──────────┘
            │                           │
            │ workspace dir gone        │ canopy switch
            ▼                           ▼
      ┌──────────┐               (resurrect tmux,
      │ orphaned │                attach, do NOT
      └──────────┘                re-run setup)
            │
            │ user confirms drop
            ▼
         (removed)
```

State transitions:
- **`setting_up`** → row exists, `scripts.setup` running. `canopy new` on a `setting_up` row fast-fails ("currently setting up, try again").
- **`ready`** → workspace dir on disk + tmux session alive. `canopy switch` attaches.
- **`stopped`** → workspace dir on disk, tmux session DEAD (laptop reboot, `tmux kill-server`, etc.). `canopy switch` resurrects: rebuilds the tmux session with the same panes/dirs/commands and re-launches `scripts.run` in the server pane, but **does NOT re-run `scripts.setup`** (DB exists, deps installed). Claude pane picks up its prior conversation automatically because `~/.claude/projects/<dir-hash>/` is dir-keyed.
- **`broken`** → `scripts.setup` failed. `last_error` captures the message; `canopy switch` shows the path to the log entry. User runs `canopy rm` to clean up.
- **`orphaned`** → state row exists, workspace dir GONE from disk. Surfaced in TUI with `!` badge. `canopy switch` prompts confirm-drop. Never silently pruned (user might have unmounted a drive, intends to remount).

### Idempotency on `canopy new`

`canopy new` (no arg) generates a random name; collision with an existing workspace is unlikely (3600 combinations) but handled by regenerate-on-collision in `namegen`. The cases below apply to `canopy new --name <n>` and to the regenerated case if it ever collides:

| Existing state                          | Behavior                                                                          |
|-----------------------------------------|-----------------------------------------------------------------------------------|
| Workspace row exists, status `ready`     | Error: "already exists. Run `canopy switch <name>` to attach."                   |
| Workspace row exists, status `setting_up`| Error: "currently setting up, try again in a moment."                            |
| Workspace row exists, status `broken`    | Error: "previous setup failed. Run `canopy rm <name>` first."                    |
| Workspace row exists, status `stopped`   | Error: "tmux session stopped. Run `canopy switch <name>` to resurrect."          |
| Workspace row exists, status `orphaned`  | Error: "workspace dir missing. Run `canopy rm <name>` to drop."                  |
| No workspace row, branch exists in git   | Error: "branch already exists in git. Use `canopy adopt <name>` (v0.5) or pick another name." |
| No workspace row, dir exists at target path | Error: "directory already exists at <path>. Remove or pick another name."     |
| Nothing exists                           | Happy path: setting_up → run scripts.setup → ready                               |

Implemented as sentinel errors (`ErrWorkspaceExists`, `ErrSettingUp`, ...) for clean test assertions via `errors.Is`.

Also: `canopy new` includes built-in port-exhaustion handling. The port allocator stops after probing the full 3000-3999 range and returns `ErrNoPortsAvailable` rather than looping forever.

### Logging & observability

- **Library:** stdlib `log/slog`, JSON output. Zero external deps.
- **Destination:** `~/.canopy/log/canopy.log`, append mode, line-delimited JSON.
- **Levels:** INFO default, DEBUG when `--debug` flag passed.
- **Pattern:** every package gets a top-of-file `var log = clog.Pkg("<name>")`. Then `log.Info("workspace.created", "branch", b, "port", p, "duration_ms", elapsed)` everywhere.
- **What gets logged at INFO:** every `Create`/`Remove`/state transition, every hook command + exit code + duration, every reconciliation result, every error.
- **What gets logged at DEBUG:** each shell-out's stdout/stderr, every state.json read/write, every flock acquire/release.
- **Rotation:** none in v0. File grows; `canopy doctor` (v0.5) will offer to rotate.
- **Error chain visibility:** errors wrapped with `%w` produce log lines like `{"level":"error","msg":"canopy new: hooks: bundle install: exit status 1"}` — readable, grep-able.

### Error-handling convention

Documented in `CLAUDE.md` so future-Claude follows it. Codified rules:

1. **Wrap with `%w`:** `return fmt.Errorf("canopy new: %w", err)`. Never lose the chain.
2. **Sentinels for known cases:** `var ErrBranchExists = errors.New("branch already exists")`. Tests use `errors.Is(err, ErrBranchExists)`.
3. **Last return value is `error`:** `(value, error)`, no exceptions.
4. **No panic outside `main()`.** Validation belongs in returned errors, not `panic`.
5. **Errors are logged at the boundary that handles them**, not at every level — wrap as you propagate, log when you decide what to do.

### Failure modes & concurrency

State mutations and port allocation must be atomic — two terminals running `canopy new` in parallel would otherwise race on `state.json` and on port assignment.

- **Lock file:** `~/.canopy/state.json.lock`, held via `flock(2)` (`golang.org/x/sys/unix`) for the entire read-modify-write window. All writers go through one helper; the TUI itself is read-mostly and tolerates eventual consistency on refresh.
- **Setup status row:** `canopy new` writes the worktree row with `status: "setting_up"` *before* hooks run. On hook success, status flips to `"ready"` and tmux is created. On hook failure, status flips to `"broken"`, the error is captured, tmux is *not* attached, and the user sees the row in the TUI marked broken with `?` showing the error.
- **Port allocation:** inside the lock, scan state.json for in-use ports, then probe the next candidate via `net.Listen("tcp", ":N")` to catch ports held by external processes (Docker, leftover puma). First port that passes both checks wins.
- **Signal handling:** SIGINT during a hook kills the running hook process group, then runs the corresponding teardown hooks before exiting. SIGINT during the TUI is a clean shutdown (tmux sessions persist).
- **Orphan cleanup:** `canopy doctor` (v0.5) lists tmux sessions matching the project prefix that lack a state.json row, and worktree dirs on disk that lack a row. v0 leaves these alone; manual cleanup is documented in the README.

### Known tricky bits (don't underestimate)

These are the parts that will eat a session if approached naively:

1. **Tmux attach from inside Bubbletea.** You can't just `os/exec` `tmux attach` while Bubbletea owns the alt screen. Use `tea.ExecProcess` (or `Program.ReleaseTerminal()` + `syscall.Exec`) to hand the terminal to tmux cleanly, and decide what happens when the user detaches with `prefix-d` (return to TUI, or exit?). Recommendation: return to TUI.
2. **Hook output streaming.** `bundle install` is slow and the user wants to see progress, not a frozen TUI. Run hooks via `os/exec` with stdout/stderr piped into a Bubbletea-friendly `tea.Msg` stream, displayed in a "running setup..." view.
3. **Stdin for hooks.** If a hook needs interactive input (rare, but `gem install` can prompt), stdin must reach it. Either declare hooks non-interactive in v0 (recommended), or do a full PTY handoff (defer to v0.5).
4. **Branch names with slashes.** Sanitize for both tmux session names *and* on-disk paths: `feature/oauth` → directory `feature-oauth`, tmux session `cravd-feature-oauth`, but the actual git branch stays `feature/oauth`.
5. **Version reporting.** `go install ...@latest` and `goreleaser` produce different binaries. Use `runtime/debug.ReadBuildInfo()` for `canopy --version` so both paths report sanely.

### Subcommands (scripting underneath)

```
canopy                          # opens TUI (default), discovers project via canopy.json walk-up
canopy new                      # generates random name (bold-falcon), creates workspace, attaches
canopy new --name <n>           # explicit name override (rare; mostly for scripting)
canopy rm <name>                # runs scripts.archive + tmux kill + git worktree remove (confirms)
canopy ls                       # one line per workspace, machine-friendly
canopy switch <name>            # attach (ready) / resurrect (stopped) / show error (broken) / confirm-drop (orphaned)
```

`canopy` resolves the active project by walking up from cwd to find `canopy.json`. If none: error with "no canopy.json found in cwd or any parent directory."

### Random workspace names

Names follow a `<adjective>-<noun>` pattern: lowercase, hyphen-separated. Examples: `bold-falcon`, `silent-otter`, `quiet-pine`, `swift-comet`. Implementation lives in `internal/namegen/` with two embedded string slices (~60 adjectives × ~60 nouns = 3600 combinations). Collision check: if the generated name exists in state.json, regenerate.

Why random:
- Removes the "what should I call this branch" friction at workspace-creation time. The hard naming decision happens later, when the work is done and the AI (or you) can suggest something descriptive based on commits.
- Branches start with the random name. When you later rename via `git branch -m bold-falcon feat/oauth-rotation`, canopy's reconcile picks up the new branch via `git worktree list --porcelain` and updates the `branch` field in state.json. The workspace `name` stays `bold-falcon` (stable identifier).
- TUI shows both: workspace name as the row label (always stable, easy to navigate to), current branch as a sub-line (descriptive, what you'd put in a PR).

`canopy doctor` (config + tool-version validator) and the `-p <project>` flag are deferred to v0.5 alongside multi-project support.

### Test plan (v0)

Stdlib `testing` only. No testify, no ginkgo. Tests live next to code (`foo.go` → `foo_test.go`). Table-driven where it fits.

**Three CRITICAL tests (write first):**
1. `state.WithLock` — parallel writers serialize correctly.
2. `port.Allocate` — two concurrent calls produce distinct ports under contention; exhaustion returns `ErrNoPortsAvailable`.
3. `workspace.Create` E2E — happy path on a scratch repo, end-to-end.

**Per-package happy-path coverage (~12 unit tests):**
- `git`: Add (happy + branch exists + sanitize), Remove (happy), Sanitize (table-driven: `feature/x`, `feature/sub/x`, empty, special chars).
- `tmux`: Create (happy), HasSession (true + false), Kill (happy).
- `hooks`: Render (substitution + missing var error), Run (happy + middle-fails + non-zero exit).
- `state`: Load (missing → empty + happy + corrupt → error), Save (atomic via tmpfile+rename).
- `config`: Discover (walk-up from cwd, happy + not-found), Load (happy + missing + bad JSON).
- `workspace`: Reconcile (all 5 statuses produce correct results), Resurrect (stopped → ready without scripts.setup re-run).

**E2E tests (build-tag `e2e`, slow):**
1. `canopy new <branch>` end-to-end on a scratch git repo with mocked-cheap hooks (`echo` instead of `bundle install`).
2. Resurrection: create → kill tmux session → switch → verify session rebuilt with same panes.

**Test infrastructure:**
- E2E uses `t.TempDir()` for canopy state and `tmux -L canopy-test` for a scoped tmux socket (won't pollute user's tmux).
- A `testdata/scratch-repo/` git repo committed to the canopy repo.
- `go test ./...` runs unit tests fast (<5s); `go test -tags=e2e ./...` runs the E2E pair.

The full coverage diagram lives in the test plan artifact at `~/.gstack/projects/canopy/avi-main-eng-review-test-plan-20260427-170120.md`. The other ~50 paths there grow with the code as bugs surface.

### Crash survival

Tmux sessions are durable by design — they live in the tmux server, not in canopy. When canopy starts, it reads state.json and queries `tmux has-session -t <name>` per row to mark which sessions are alive. Closing canopy or `kill -9`-ing it has zero effect on running work. Reboot survives via the `stopped` state + `Resurrect()`.

## Success Criteria

- [ ] `canopy new fix-bug` from the cravd repo (with `canopy.json` migrated from `conductor.json`) completes in under 15 seconds (target: 10s) and leaves you in an attached tmux session ready to code.
- [ ] `canopy` opens the TUI in <100ms with the workspace list visible.
- [ ] `canopy rm fix-bug` runs `scripts.archive` (DB drop, server kill), removes the worktree, prunes state.
- [ ] After laptop reboot, `canopy` shows all workspaces as `stopped`; `canopy switch fix-bug` resurrects in ~2s and the claude pane has its prior conversation history.
- [ ] Concurrent `canopy new` from two terminals → distinct ports, no state corruption.
- [ ] One `vhs`-generated GIF demoing new + switch + remove for the README.
- [ ] AUR package installs cleanly on a fresh Omarchy box (deferred to a separate post-v0.1 session).
