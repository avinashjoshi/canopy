## Affected Pages/Routes

This is a TUI, not a web app. The "routes" are subcommands and TUI views.

**CLI subcommands to test:**
- `canopy` (no args) — TUI launches in <100ms with worktree list visible
- `canopy new <branch>` — full lifecycle: state row → port → git → hooks → tmux → ready
- `canopy rm <branch>` — teardown lifecycle: hooks → tmux kill → git remove → state prune
- `canopy ls` — machine-friendly output for scripting
- `canopy switch <branch>` — attach for `ready`, resurrect for `stopped`, error log for `broken`, confirm-drop for `orphaned`
- `canopy --version` — prints build info from `runtime/debug.ReadBuildInfo()`
- `canopy --debug` — bumps slog to DEBUG level

**TUI views to test:**
- List view — selection moves with j/k, badges render correctly per status (`ready`/`stopped`/`broken`/`orphaned`/`setting_up`)
- New-worktree modal — `n` opens textinput, validates non-empty, calls Create
- Setup-running view — streamed hook output displayed live
- Help overlay — `?` toggles
- Confirm-delete view — `d` opens; y/n required

## Key Interactions to Verify

**The wedge (highest priority):**
- `canopy new fix-bug` on cravd config → tmux session attached in <15s with 4 panes (nvim, claude, shell, server)
- Port appears in `state.json` and the dev server actually binds to it
- Hook output streams live in the TUI (not a frozen "running..." view)

**Resurrection (the killer demo from issue 1E):**
- After laptop reboot, `canopy` opens → status is `stopped` for all rows (tmux gone, dirs alive)
- `canopy switch fix-bug` rebuilds the tmux session in ~2s, attaches, and `claude` pane picks up prior conversation history (since `~/.claude/projects/<dir-hash>/` is dir-keyed)

**Idempotency (issue 1C):**
- `canopy new fix-bug` twice in a row → second invocation fast-fails with explicit error "fix-bug already exists (status: ready). Run `canopy switch fix-bug` to attach, or `canopy rm fix-bug` first."
- Run `canopy new fix-bug` while previous is `setting_up` → fast-fail with "currently setting up, try again in a moment"

**Multi-pane setup:**
- Verify `nvim`, `claude`, `$SHELL`, `bin/dev` all spawn correctly with the right CWD (worktree dir) and the env block from project YAML
- `bin/dev` actually binds to the allocated port (i.e. PORT env var propagates correctly)

**Reconciliation (issue 1D + 1E):**
- Manually `rm -rf ~/Work/cravd/worktrees/fix-bug`, then run `canopy` → row shows `orphaned` with `!` badge
- Manually `tmux kill-session -t cravd-fix-bug`, then run `canopy` → row shows `stopped`
- `canopy ls` reflects the current reconciled view

**TUI smoothness:**
- Selection arrow keys feel responsive (no >100ms lag)
- `enter` on selection cleanly hands the terminal to tmux and returns on `prefix-d`
- `q` exits TUI without killing tmux sessions (verify with `tmux ls` after)

## Edge Cases

**Concurrency (CRITICAL):**
- Two terminals run `canopy new fix-bug` and `canopy new fix-other` in parallel → distinct ports allocated, no `state.json` corruption, both succeed
- Two terminals run `canopy new fix-bug` simultaneously → one wins, the other gets the idempotency error

**Port allocation:**
- Manually bind port 3000 with `python3 -m http.server 3000`, then `canopy new fix-bug` → canopy probes via `net.Listen`, picks 3001 (or higher)
- Run 5 worktrees → ports 3000-3004, no collisions

**Branch name edge cases:**
- `canopy new feature/oauth` → directory `feature-oauth`, tmux session `cravd-feature-oauth`, git branch stays `feature/oauth`
- `canopy new feature/sub/x` → directory `feature-sub-x`, git branch stays `feature/sub/x`
- Empty / whitespace branch name → validation error in TUI textinput, never reaches git

**Hook failures:**
- Hook exit non-zero (simulate by adding `false` to setup hooks) → status flips to `broken`, tmux not attached, error captured to `~/.canopy/log/canopy.log`
- SIGINT during `bundle install` → process group killed, teardown hooks run, status: `broken`, log shows interrupt

**State.json edge cases:**
- Missing `state.json` → empty list, no crash
- Corrupted `state.json` (manually break the JSON) → clear error, refuse to mutate, suggest backup-and-recreate
- `state.json.lock` held by stale process → after timeout, error with PID guidance

**Config edge cases:**
- Missing `~/.canopy/projects/cravd.yaml` → clear error: "no project config found"
- Bad YAML syntax → line-aware error from `yaml.v3`
- Required field missing (e.g., no `worktrees_path`) → validation error names the field

## Critical Paths

These end-to-end flows MUST work for v0 to be considered shipped:

1. **The wedge demo (E2E):**
   `canopy new fix-bug` from clean state → 10-15s later attached to tmux with all 4 panes operational, server bound to allocated port, claude pane responsive. This is the vhs GIF.

2. **Reboot survives (E2E):**
   Create 2 worktrees with `canopy new`, kill all tmux servers (`tmux kill-server`), run `canopy` → both rows show `stopped`, `enter` resurrects each in ~2s with claude history intact.

3. **Concurrent new (E2E + concurrency):**
   Two parallel `canopy new <distinct-branch>` invocations → both succeed, distinct ports, no corruption.

4. **Hook failure recovery (E2E):**
   Misconfigure setup hooks (e.g., `bundle install` against missing Gemfile) → status `broken`, tmux NOT attached, log file contains stderr, `canopy rm` cleans up the half-state.

5. **Cleanup (E2E):**
   `canopy rm fix-bug` → teardown hooks run, DB dropped, server killed, tmux session gone, worktree dir gone, state row removed. Verify via `tmux ls`, `ls ~/Work/cravd/worktrees/`, and `psql -l`.

## Test infrastructure recommendations

- Use stdlib `testing` only (no testify, no ginkgo) — keeps the first-time-Go learning curve clean.
- Table-driven tests for `Sanitize()`, `Render()`, status transitions.
- E2E tests use `t.TempDir()` for canopy state and a scoped `tmux -L canopy-test` socket so they don't clobber the user's running tmux.
- A `testdata/scratch-repo/` git repo (committed) for git+worktree tests.
- Run E2E with `-tags=e2e` build tag so unit tests stay fast (`go test ./...` skips E2E by default).

## Regression rule

This is a greenfield project; no regressions exist yet. The first incident in production becomes the first regression test. Add `// regression: <issue-link>` as a comment on any test added in response to a real bug.
